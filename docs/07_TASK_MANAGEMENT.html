Feature 07

Task Management

The actionable layer of every investigation. Tasks keep fintech ops teams accountable — who does what, by when, in which case. From document verification to compliance escalations, nothing falls through the cracks.

Module: internal/tasks
DB Tables: tasks, task_comments
Stack: Go + River + Next.js
Phase: MVP
01

Feature Overview

Every case in OpsOwl generates a stream of work: verify KYC documents, call the customer, check bank statements, escalate to the compliance officer, review the AI-generated fraud summary. Without a structured task layer, this work is tracked in chat messages, mental notes, or external spreadsheets — all of which break down at scale.

Task Management is the accountability engine of OpsOwl. Every task is linked to a case. Tasks have owners, deadlines, priorities, and a clear lifecycle. The River-backed background job ensures overdue tasks surface immediately — no polling required from the frontend.

Design Principle: Tasks are always subordinate to Cases. A task cannot exist without a parent case. Timeline event linking is optional metadata — it adds context but does not gate task creation.

03

Database Schema

Two tables: tasks (core task record) and task_comments (threaded discussion on each task). Both follow the standard OpsOwl conventions: UUID v4 primary keys, TIMESTAMPTZ timestamps, and soft deletes via deleted_at.

PostgreSQL 18.4 DDL
-- ─────────────────────────────────────────────
-- Enums
-- ─────────────────────────────────────────────
CREATE TYPE task_status AS ENUM (
    'todo',
    'in_progress',
    'done',
    'cancelled'
);

CREATE TYPE task_priority AS ENUM (
    'critical',
    'high',
    'medium',
    'low'
);

-- ─────────────────────────────────────────────
-- tasks
-- ─────────────────────────────────────────────
CREATE TABLE tasks (
    id                UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    case_id           UUID            NOT NULL REFERENCES cases(id) ON DELETE RESTRICT,
    created_by        UUID            NOT NULL REFERENCES users(id),
    assigned_to       UUID                     REFERENCES users(id),  -- nullable
    timeline_event_id UUID                     REFERENCES timeline_events(id) ON DELETE SET NULL,
    title             TEXT            NOT NULL CHECK (char_length(title) <= 255),
    description       TEXT,
    status            task_status     NOT NULL DEFAULT 'todo',
    priority          task_priority   NOT NULL DEFAULT 'medium',
    due_date          TIMESTAMPTZ,
    completed_at      TIMESTAMPTZ,
    is_overdue        BOOLEAN         NOT NULL DEFAULT FALSE,  -- set by River job
    is_ai_suggested   BOOLEAN         NOT NULL DEFAULT FALSE,
    created_at        TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    deleted_at        TIMESTAMPTZ                               -- soft delete
);

-- Indexes
CREATE INDEX idx_tasks_case_id      ON tasks(case_id)                         WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_assigned_to   ON tasks(assigned_to)                    WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_status        ON tasks(status)                          WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_due_date      ON tasks(due_date)                        WHERE deleted_at IS NULL AND status != 'done';
CREATE INDEX idx_tasks_is_overdue    ON tasks(is_overdue)                      WHERE deleted_at IS NULL AND is_overdue = TRUE;
CREATE INDEX idx_tasks_case_status   ON tasks(case_id, status, priority)     WHERE deleted_at IS NULL;

-- Auto-update updated_at
CREATE TRIGGER tasks_updated_at
    BEFORE UPDATE ON tasks
    FOR EACH ROW EXECUTE PROCEDURE trigger_set_timestamp();

-- ─────────────────────────────────────────────
-- task_comments
-- ─────────────────────────────────────────────
CREATE TABLE task_comments (
    id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id     UUID        NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    author_id   UUID        NOT NULL REFERENCES users(id),
    content     TEXT        NOT NULL CHECK (char_length(content) <= 4096),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at  TIMESTAMPTZ
);

CREATE INDEX idx_task_comments_task_id ON task_comments(task_id) WHERE deleted_at IS NULL;

CREATE TRIGGER task_comments_updated_at
    BEFORE UPDATE ON task_comments
    FOR EACH ROW EXECUTE PROCEDURE trigger_set_timestamp();
is_overdue flag: Stored as a boolean column rather than a computed expression. The River background job sets it to TRUE when due_date < NOW() and task is not done/cancelled. This avoids re-computing the predicate on every query and allows indexed lookups on the overdue state.
04

SLA / Due Date Tracking

Due-date enforcement is handled by a River background job that runs on a fixed 5-minute schedule. There is no database trigger — the River job is the single source of overdue truth, keeping the DB schema clean and making the logic testable in isolation.

River Job: OverdueTaskScanJob
Schedule: Every 5 minutes (River cron expression: */5 * * * *)
Query: UPDATE tasks SET is_overdue = TRUE WHERE due_date < NOW() AND status NOT IN ('done','cancelled') AND is_overdue = FALSE
On Update: For each row updated, enqueue a TaskOverdueNotificationJob targeting the assignee and case owner.
Idempotent: The is_overdue = FALSE predicate ensures already-flagged tasks are not re-notified.
River Job: DueDateReminderJob
Schedule: Every 15 minutes (checks upcoming due dates)
24-Hour Reminder: due_date BETWEEN NOW() + INTERVAL '23h 45m' AND NOW() + INTERVAL '24h 15m'
1-Hour Reminder: due_date BETWEEN NOW() + INTERVAL '45m' AND NOW() + INTERVAL '1h 15m'
Dedup: A task_reminder_sent JSONB column or a separate task_reminders log table tracks which windows have already fired.

Overdue Resolution

When a task transitions to done or cancelled, the API handler sets is_overdue = FALSE immediately — no need to wait for the River job. This ensures real-time accuracy in the task list UI.

Notification Channel

Phase 1: in-app notifications (notification bell). SSE stream pushes the event. Phase 2: add email/Slack hooks via the notification module. River job payload carries enough data to route to any future channel without schema changes.

05

API Endpoints

All endpoints follow the OpsOwl REST convention: /api/v1/ prefix, response envelope {data, meta, error}, cursor-based pagination for list endpoints, ISO 8601 UTC timestamps.

POST /api/v1/cases/:id/tasks Create a task under a case. Body: title, description?, priority, due_date?, assigned_to?. Returns the created task. Auth
GET /api/v1/cases/:id/tasks List tasks for a case. Query: status, priority, assigned_to, overdue=true, cursor pagination. Public
GET /api/v1/tasks "My Tasks" — cross-case tasks assigned to the authenticated user. Filter: status, overdue. Sorted by due_date ASC, priority DESC. Auth
GET /api/v1/tasks/:id Fetch a single task with full detail: case reference, assignee info, comment count, AI suggestion metadata. Public
PUT /api/v1/tasks/:id Update task fields (title, description, priority, due_date, assigned_to, status). Validates state machine transitions server-side. Auth
POST /api/v1/tasks/:id/complete Shorthand complete action. Sets status=done, completed_at=NOW(), is_overdue=FALSE. Returns updated task. Idempotent. Auth
DELETE /api/v1/tasks/:id Soft delete — sets deleted_at. Returns 204 No Content. Only case owner or task creator can delete. Owner
POST /api/v1/tasks/:id/comments Add a comment to a task. Body: content (max 4096 chars). Returns created comment with author profile. Auth
GET /api/v1/tasks/:id/comments List comments for a task, newest-first, cursor paginated. Includes author display name and avatar URL. Public

06

AI Integration

OpsOwl's AI Copilot can suggest tasks by analyzing case documents, timeline events, and past investigation patterns. Suggested tasks are non-binding — the analyst always has full control over accept, modify, or reject before any task is persisted.

AI Copilot Task Extraction Flow

The Copilot calls the Python AI service's POST /ai/v1/cases/:id/extract-actions endpoint. The AI service returns a list of suggested task objects with title, description, priority, and reasoning. The Go handler stores them with is_ai_suggested=TRUE and a status='todo'. They are surfaced to the analyst in a special "AI Suggested" section of the task list — separate from the confirmed task backlog.

AI Suggested
Cross-check Aadhaar address with loan application address
AI detected a mismatch between the Aadhaar address (Mumbai) and the loan application address (Pune). Recommend manual verification with the customer before disbursement.

Accept: Sets is_ai_suggested=TRUE flag permanently for audit, task is promoted to the main task list.
Edit & Accept: Opens task form pre-filled with AI suggestion — analyst modifies before saving.
Reject: Soft-deletes the suggested task. Rejection reason is logged for AI feedback loop.

Audit Trail: All AI-suggested tasks retain is_ai_suggested=TRUE even after analyst edits. This is immutable once set — it powers compliance reporting on how often AI recommendations were acted upon vs. rejected.

Key Design Points

State Machine in Service Layer

Transition validation lives in tasks_service.go, not in the handler or DB trigger. This makes it unit-testable with a mock repo and keeps the DB schema transition-agnostic.

River Job Registration

Both River jobs are registered in module.go via the app's central River client. Schedules are defined as constants — easy to change without hunting through code.

Frontend Components

Built with Next.js 16 App Router, TypeScript strict, Tailwind v4, shadcn/ui primitives, TanStack Query v5 for server state, and Zustand for local UI state (view preference, selected task, panel open/closed).

≡
TaskList
Grouped by status columns. Accepts filter props. Uses TanStack Query with staleTime=30s. Renders TaskCard per item. Virtualized for 200+ tasks.

✎

Create/edit form. React Hook Form + Zod validation. Fields: title, description, priority select, due date picker, assignee search. Supports pre-fill from AI suggestion.
☑

Cross-case personal task list. Calls GET /api/v1/tasks. Sorted by urgency. Grouped: Overdue → Due Today → This Week → Later.

✦

List View

Dense table layout. Sortable by due_date, priority, status. Ideal for "My Tasks" view and overdue scanning. Shows all metadata inline. Default for "My Tasks" page.

Kanban View

Three columns: Todo / In Progress / Done. Drag-to-reorder within a column (basic sort order stored as integer field). Default for Case Task tab. Satisfying for status progression.

MVP Scope: Drag-to-reorder is included as a basic feature using a simple sort_order integer column. Cross-column drag (status change via drag) is Phase 2 — requires careful optimistic UI handling. For MVP, status change is done via the dropdown in the card menu.

Test Strategy

Unit State Machine Validation — Unit tests for every valid and invalid state transition in tasks_service.go. E.g., assert error when transitioning from done → in_progress.
Unit OverdueTaskScanJob — Unit test with mocked clock and mock repo. Assert that tasks where due_date < now are flagged and notifications enqueued. Assert idempotency (already-flagged tasks not re-notified).
Unit DueDateReminderJob — Test that both reminder windows (24h, 1h) trigger correctly and do not double-fire in the same window.
Integ Task Assignment Flow — Integration test using testcontainers-go Postgres. Create case → create task → assign to user → verify DB state. Confirm assigned_to FK enforced.
Integ Overdue Detection End-to-End — Insert task with past due_date, run River job manually, assert is_overdue=TRUE in DB and notification record created.
Integ Task Complete API — POST to /complete on an overdue task: assert status=done, is_overdue=FALSE, completed_at set. Assert idempotency on second call.
Integ AI Suggestion Audit — Accept an AI-suggested task, then edit it. Assert is_ai_suggested remains TRUE after all edits — immutability guaranteed.
E2E My Tasks Cross-Case View — Playwright test: create two cases with tasks assigned to the test user. Open "My Tasks" view, assert both tasks appear. Complete one, assert list updates without page reload.
E2E Kanban Drag-to-Reorder — Playwright drag simulation: reorder tasks within Todo column. Assert new sort_order persisted after page refresh.
Coverage Target: Service layer ≥ 90% unit test coverage. Repository layer ≥ 80% integration test coverage (using testcontainers-go). E2E tests cover the 3 critical user flows: create task, complete task, view My Tasks.

Feature 11 — Search

Global Search &
Full-Text Discovery

Investigators need to find anything instantly — a case by customer name, a note mentioning "fraud", a document containing a specific account number, a task assigned to a specific analyst. Global search across all entities in a single query, powered by PostgreSQL FTS with semantic augmentation via pgvector.

1

Feature Overview

In a live investigation workspace handling hundreds of cases, dozens of analysts, and thousands of notes and documents, the ability to find anything instantly is not a convenience — it is a core workflow requirement. An analyst investigating a fraud cluster needs to pull up every note mentioning "mule account" across all cases. A compliance manager needs to locate all documents containing a specific IFSC code. A supervisor needs to find every task assigned to an analyst who just went on leave.

OpsOwl Search provides a single, unified query that reaches across cases, notes, comments, documents, tasks, and timeline events simultaneously. Results are ranked by relevance, grouped by entity type, and filtered by the searcher's RBAC permissions — so analysts never see results they are not authorized to access.

☁

MVP Scope

MVP ships with PostgreSQL full-text search (tsvector/tsquery) and pgvector semantic search for document chunks. Elasticsearch integration is deferred to Phase 2 and triggered only by measured query latency exceeding 500ms consistently.

Search Technology

PostgreSQL FTS — Why
  • ✓ Adequate for records under 1 million — no new infrastructure to operate
  • ✓ Built into PostgreSQL 18.4 — zero additional services to deploy or monitor
  • ✓ ACID-consistent with application data — search index always transactionally correct
  • ✓ GIN indexes deliver sub-50ms queries for typical case loads
  • ✓ ts_rank relevance scoring available out of the box
PostgreSQL FTS — How
  • → tsvector generated column on search_index.ts_content
  • → GIN index on ts_content for fast bitset intersection
  • → Query converted with plainto_tsquery('english', $1)
  • → Results ranked via ts_rank(ts_content, query)
  • → Snippets generated via ts_headline(content, query)
📌

Semantic Search via pgvector

Document chunks are embedded using text-embedding-3-small and stored as vector(1536) in the document_chunks table. When a user searches, the query is also embedded (Python AI service) and an IVFFlat ANN search runs against document chunk vectors to find semantically similar passages — even without exact keyword matches. FTS and vector results are merged and de-duplicated before returning.

⚠

Phase 2 Trigger — Elasticsearch Migration

When P95 search query latency exceeds 500ms consistently over a 24-hour window (measured via Prometheus + Grafana), the team initiates the Elasticsearch migration. The API contract (GET /api/v1/search) does not change — only the backend implementation switches. See Section 13 for migration path.

Database Schema

search_index Table — Purpose

A centralized, denormalized index table that aggregates searchable text from all entity types into a single place. Each row represents one searchable unit of content, tagged with its entity type and linked back to the original entity and case. The ts_content column is a generated column — PostgreSQL automatically maintains it.

entity_type enum GIN index GENERATED ALWAYS River job updates 
-- ────────────────────────────────────────────────────────────
-- OpsOwl AI — Search Index Schema
-- PostgreSQL 18.4 + pgvector
-- ────────────────────────────────────────────────────────────

CREATE TYPE entity_type_enum AS ENUM (
    'case',
    'note',
    'comment',
    'document',
    'task',
    'timeline_event'
);

CREATE TABLE search_index (
    id           UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_type  entity_type_enum  NOT NULL,
    entity_id    UUID          NOT NULL,          -- FK to the source row
    case_id      UUID          REFERENCES cases(id) ON DELETE CASCADE,
    -- case_id nullable: some global entities are not case-scoped
    org_id       UUID          NOT NULL REFERENCES organizations(id),
    content      TEXT          NOT NULL,          -- raw text corpus
    ts_content   TSVECTOR      GENERATED ALWAYS AS (
                    to_tsvector('english', coalesce(content, ''))
                 ) STORED,
    updated_at   TIMESTAMPTZ   NOT NULL DEFAULT NOW()
);

-- Primary FTS index — GIN on generated tsvector
CREATE INDEX idx_search_ts_content
    ON search_index USING GIN(ts_content);

-- Filter indexes — always needed for scoped searches
CREATE INDEX idx_search_entity_type ON search_index(entity_type);
CREATE INDEX idx_search_case_id     ON search_index(case_id) WHERE case_id IS NOT NULL;
CREATE INDEX idx_search_org_id      ON search_index(org_id);
CREATE UNIQUE INDEX idx_search_entity_unique
    ON search_index(entity_type, entity_id);  -- one row per entity

-- ────────────────────────────────────────────────────────────
-- Document Chunks — semantic search via pgvector
-- ────────────────────────────────────────────────────────────

CREATE TABLE document_chunks (
    id           UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id  UUID          NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    case_id      UUID          NOT NULL REFERENCES cases(id) ON DELETE CASCADE,
    org_id       UUID          NOT NULL REFERENCES organizations(id),
    chunk_index  INT           NOT NULL,            -- ordinal within document
    content      TEXT          NOT NULL,
    embedding    vector(1536) NOT NULL,            -- text-embedding-3-small
    created_at   TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ   NOT NULL DEFAULT NOW()
);

-- IVFFlat ANN index — lists tuned for ~100k chunks
CREATE INDEX idx_chunks_embedding
    ON document_chunks USING IVFFLAT (embedding vector_cosine_ops)
    WITH (lists = 100);

CREATE INDEX idx_chunks_document_id ON document_chunks(document_id);
CREATE INDEX idx_chunks_case_id     ON document_chunks(case_id);
🔗

Index Maintenance via River

Each module (cases, notes, comments, documents, tasks, timeline) emits a SearchIndexEvent{entity_type, entity_id, operation} whenever content is created, updated, or deleted. A River background job handler picks this up and performs an INSERT INTO search_index ... ON CONFLICT (entity_type, entity_id) DO UPDATE SET content = ..., updated_at = NOW(). Deletions propagate via ON DELETE CASCADE on the source FK. The generated ts_content column updates automatically when content is written.

Search Query Flow

1

User Types Query

User opens the command palette (Cmd+K) or the search page and types a query string. Input is trimmed and validated (min 2 characters, max 200 characters).

2

Debounced Request (300ms)

Frontend debounces the query by 300ms. On the 300ms boundary, dispatches GET /api/v1/search?q=fraud+mule&types[]=note&types[]=case&limit=20. Abort controller cancels any pending in-flight request.

3

Go Handler — Auth & Parse

Go Chi handler extracts JWT claims, resolves org_id and user_id, parses query parameters, constructs SearchParams struct. Validates entity type filters against the allowed enum.

4

PostgreSQL FTS Query

Calls sqlc-generated query: SELECT entity_type, entity_id, case_id, content, ts_rank(ts_content, query) AS rank, ts_headline('english', content, query, 'MaxWords=35, MinWords=15, StartSel=<mark>, StopSel=</mark>') AS snippet FROM search_index, plainto_tsquery('english', $1) query WHERE org_id = $2 AND ts_content @@ query ORDER BY rank DESC LIMIT $3. RBAC filter applied via JOIN on accessible case_ids.

5

pgvector Semantic Query (Documents)

In parallel (goroutine), if entity types include document: calls Python AI service POST /internal/embed with query text → receives vector[1536] → runs SELECT ... FROM document_chunks WHERE org_id = $org ORDER BY embedding <=> $vec LIMIT 10. Results merged and de-duplicated by entity_id.

6

Group & Enrich Results

Go service groups results by entity_type. For each result, fetches the display title from the in-memory entity resolver (already warm from primary queries). Constructs response envelope with grouped buckets, total counts, and relevance scores.

7

Cached Response

Response cached in-process (go-cache) for 5 seconds keyed by org_id:user_id:query_hash:filters_hash. Cache skipped for case-scoped searches where live accuracy matters. Returns 200 OK with {data: {results: {...}}, meta: {total, query_ms}}.

Result Highlighting

ts_headline — PostgreSQL Native Highlighting

PostgreSQL's ts_headline() function generates a short excerpt from the content with matched terms wrapped in configurable HTML tags. OpsOwl uses <mark> tags so that frontend styling is consistent with the rest of the app. 

-- ts_headline configuration used in OpsOwl search queries
ts_headline(
    'english',              -- text search configuration
    search_index.content,   -- source text
    plainto_tsquery('english', $1),  -- query
    'MaxWords=35,           -- max words in snippet
     MinWords=15,           -- min words in snippet
     ShortWord=3,           -- ignore words shorter than 3 chars in highlighting
     HighlightAll=false,    -- only highlight if matches exist
     MaxFragments=2,        -- show up to 2 non-contiguous fragments
     FragmentDelimiter=" … ", -- separator between fragments
     StartSel=<mark>,      -- open tag
     StopSel=</mark>'      -- close tag
)

Frontend renders the snippet as dangerouslySetInnerHTML with a strict allowlist sanitizer (only <mark> permitted). The <mark> element is styled via Tailwind: bg-cyan-400/20 text-cyan-300 rounded px-0.5. No raw HTML injection risk as the snippet source is the database, not user-controlled HTML.

RBAC on Search

🔒

Security Principle

Search is not a backdoor to restricted data. An analyst searching for "fraud" cannot discover cases that are not in their accessible case set. Permission enforcement happens at the database query level — not the result-filtering level — so restricted results are never fetched.

Role Accessible Cases Search Scope Implementation
analyst Cases assigned to them, or cases where they have a task/note Only their case subset. Cannot see other analysts' cases. AND case_id = ANY(SELECT case_id FROM case_members WHERE user_id = $user)
manager All cases within their organization Full org-wide search. Can see all analysts' work. AND org_id = $org_id
admin All cases across all orgs (super admin only) Full platform search (internal tooling only). No case filter applied; org filter still applies for org admins.
ⓘ

Global Content (non-case-scoped)

Some entities (e.g. global templates) have case_id = NULL in search_index. These are returned to all users in the same organization. Org-level isolation is always enforced via org_id — cross-tenant search is architecturally impossible.

Search Index Maintenance

Initial Full Index Build

Run as a one-time migration step after schema creation. A Go CLI command opsowl-admin index --rebuild iterates all entity tables in batches of 500 rows, builds the content string, and upserts into search_index. Runs inside a single long-lived transaction per batch to avoid partial states. ETA: ~2 minutes for 50,000 entities.

Incremental Updates (River)

Every write path (note saved, case updated, document uploaded, task created) enqueues a search_index_sync River job with a 1-second delay (deduplicated by entity key). River worker calls UPSERT INTO search_index ... ON CONFLICT DO UPDATE. Since ts_content is a generated column, no explicit tsvector computation in application code.

Deletion Propagation

Soft-deleted entities: River job sets content = '' in search_index (empty tsvector matches nothing). Hard deletes: ON DELETE CASCADE on case_id FK propagates automatically. Entity-level deletes require explicit River job to delete the search_index row.

Drift Recovery

Nightly River scheduled job (search_index_audit) runs at 02:00 UTC: counts rows in each entity table vs search_index, identifies missing or stale entries (updated_at delta > 1 hour), and re-enqueues sync jobs for drifted entities. Alert fires if drift exceeds 0.1% of total entities.

Phase 2 — Elasticsearch Migration Path

When to Migrate

The migration is triggered when P95 search latency exceeds 500ms consistently over a 72-hour window, as measured by Prometheus metrics exported from the Go search handler. This corresponds to roughly 2–5 million indexed entities at typical query complexity.

Do not migrate early. PostgreSQL FTS is fully adequate and operationally simpler. Elasticsearch adds significant operational overhead (cluster management, index mapping, replication), which is not justified until load demands it.

Zero-Downtime Migration Steps
1

Deploy Elasticsearch Cluster

Provision ES cluster alongside existing PostgreSQL. No changes to application yet.

2

Dual-Write Mode

Enable feature flag search.dual_write=true. Search index sync River job writes to both PostgreSQL search_index and Elasticsearch index simultaneously. API still reads from PostgreSQL.

3

Backfill Elasticsearch

Run opsowl-admin index --rebuild --target=elasticsearch to bulk-index existing data. Verify index counts match PostgreSQL row counts within 0.1%.

4

Shadow Read Mode (Canary)

Feature flag search.read_from=elasticsearch for 5% of traffic. Compare result quality and latency. Fix any discrepancies in mapping or tokenization.

5

Full Cutover

Increase canary to 100%. Disable PG FTS queries. The GET /api/v1/search endpoint URL does not change. Remove search_index writes after 30-day stability period.

🔗

API Contract Stability

The search API contract — request parameters, response schema, highlighting format, cursor pagination — remains identical throughout the migration. Frontend code is never touched. Only the internal/search/service/search_service.go backend implementation changes behind the interface.

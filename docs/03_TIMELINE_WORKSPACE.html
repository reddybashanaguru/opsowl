Feature Overview

Investigation is fundamentally an exercise in understanding chronology. Who did what, when, and why — in the correct order. Most enterprise tools scatter this information: case notes live in one tab, documents in another, task history in a third, and audit logs are buried in an admin panel nobody opens. OpsOwl AI inverts this completely.


The Timeline Workspace is a single, unified, chronological stream of every event that has ever occurred on a case. Case status changes, documents uploaded, AI analyses run, notes written, tasks completed, logins by team members, SLA warnings fired — every atom of case activity is an event in this stream. Investigators work from the timeline. The timeline is the case.

Unified
Every system, every user, every AI action in one stream. No tab-switching.
Immutable
Events are never deleted or modified. Append-only for audit integrity.
Real-time
New events pushed via SSE the moment they occur. No page refresh needed.
Back-datable
Events carry real-world timestamps (occurred_at), not just system-log timestamps.

03

Database Schema

⚡
Key Design Insight: occurred_at vs created_at
occurred_at is the real-world timestamp of when the event actually happened — e.g., a document was signed on Dec 5 but uploaded into the system on Dec 8. created_at is when the database row was inserted. The timeline sorts by occurred_at DESC. This distinction is fundamental to investigation accuracy — regulators and audit trails care about the real-world chronology, not the logging chronology.
SQL · PostgreSQL 18.4 migrations/005_timeline_events.sql 
-- Event type enum: append-only, never remove values
CREATE TYPE timeline_event_type AS ENUM (
  'case_created', 'case_status_changed', 'case_assigned', 'case_tagged',
  'document_uploaded', 'document_processed', 'document_ai_analyzed',
  'note_added', 'note_edited', 'comment_added',
  'task_created', 'task_completed', 'task_overdue',
  'ai_query', 'ai_summary_generated', 'ai_action_suggested',
  'user_login', 'user_action',
  'sla_warning', 'sla_breached',
  'notification_sent'
);

CREATE TYPE timeline_event_source AS ENUM (
  'system', 'user', 'ai'
);

-- Core timeline events table
CREATE TABLE timeline_events (
  -- Standard OpsOwl fields
  id            UUID                       PRIMARY KEY DEFAULT gen_random_uuid(),
  created_at    TIMESTAMPTZ                NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ                NOT NULL DEFAULT now(),
  deleted_at    TIMESTAMPTZ,               -- soft delete; NULL = active

  -- Domain fields
  case_id       UUID                       NOT NULL
                REFERENCES cases(id)       ON DELETE CASCADE,
  event_type    timeline_event_type        NOT NULL,
  source        timeline_event_source      NOT NULL,
  actor_id      UUID                               -- NULL for pure system events
                REFERENCES users(id)       ON DELETE SET NULL,

  -- The key insight: real-world time vs. insertion time
  occurred_at   TIMESTAMPTZ                NOT NULL,   -- Real-world event time (sortable)
                                                          -- Events can be back-dated (e.g.
                                                          -- doc signed 3 days ago, uploaded now)

  -- Flexible payload — schema varies by event_type
  payload       JSONB                      NOT NULL DEFAULT '{}',

  -- Optional structured metadata (search, filtering)
  metadata      JSONB                      NOT NULL DEFAULT '{}'
  -- e.g. {"tags": ["fraud", "kyc"], "is_system_generated": true}
);

-- ── Indexes ──────────────────────────────────────────────

-- Primary query pattern: all events for a case, sorted newest first
CREATE INDEX idx_timeline_case_occurred
  ON timeline_events (case_id, occurred_at DESC)
  WHERE deleted_at IS NULL;

-- Filter by event type within a case
CREATE INDEX idx_timeline_case_event_type
  ON timeline_events (case_id, event_type)
  WHERE deleted_at IS NULL;

-- Filter by source (system / user / ai)
CREATE INDEX idx_timeline_source
  ON timeline_events (case_id, source)
  WHERE deleted_at IS NULL;

-- Actor lookup (who did what across all cases)
CREATE INDEX idx_timeline_actor
  ON timeline_events (actor_id, occurred_at DESC)
  WHERE actor_id IS NOT NULL AND deleted_at IS NULL;

-- JSONB GIN index for payload search
CREATE INDEX idx_timeline_payload_gin
  ON timeline_events USING gin (payload);

-- Auto-update updated_at
CREATE TRIGGER trg_timeline_events_updated_at
  BEFORE UPDATE ON timeline_events
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
🔒
Immutability Rule
Timeline events are never hard-deleted or modified after creation. The deleted_at soft-delete exists only for data-retention policy compliance (e.g., GDPR erasure) and is only ever set by the platform admin role. The application layer has no DELETE permission on this table. A Row-Level Security policy enforces this at the DB layer.
04

Event Sourcing

OpsOwl AI uses a lightweight event sourcing pattern — not full CQRS/event-store purity, but a pragmatic hybrid where every meaningful state mutation also produces an immutable timeline event. The event store becomes the source of truth for audit and reconstruction.

1
Business Operation Executes
e.g., cases.UpdateStatus(ctx, caseID, newStatus) — the domain service runs its validation and DB mutation inside a transaction.
2
Event Emitted — Same Transaction
The service calls timeline.Emit(ctx, tx, TimelineEvent{...}). The event INSERT happens in the same DB transaction — guaranteed atomicity. If the business mutation fails, no event is written.
3
Transaction Commits
Both the state change and the timeline event are committed atomically. The event store is always consistent with application state.
4
Post-Commit: SSE Dispatch
After commit, the event dispatcher publishes to a Go channel. The SSE hub receives this and fans out to all connected clients watching that case's stream.
5
Client Receives Real-time Update
Browser receives the SSE event, React inserts it at the top of the virtualized timeline list with a "New" indicator — no reload required.
🧩
Audit Reconstruction
Because every state change produces an immutable event, the full case history can be reconstructed purely from the timeline_events table. This is the basis for the "Case Audit Report" export feature — no need to join across 12 tables. The regulator gets a clean, timestamped, sourced narrative.

Real-time Updates via SSE

Event Flow Architecture

Go Domain Service
timeline.Emit(ctx, tx, event)
DB INSERT (same tx)
↓
Post-commit Hook
Go channel publish
SSE Hub
↓
SSE Hub
Fan-out to N clients
Browser EventSource
Client Connection
Browser opens EventSource with JWT in Authorization header via ?token= query param (SSE cannot set custom headers). Server validates RS256 JWT and registers client in hub keyed by case_id.
Reconnect Handling
Browser EventSource auto-reconnects. Client sends Last-Event-ID header. Server replays missed events from timeline_events where id > last_seen_id before resuming live stream.
Heartbeat
Server sends a ping event every 30 seconds. If client misses 3 consecutive pings, it closes and reopens the connection. This keeps NAT/proxy connections alive.
Hub Cleanup
Hub tracks all connections per case in a sync.Map[caseID → []chan Event]. When a client disconnects (context done), it is removed from the map. Zero active clients = zero goroutines.
Go internal/timeline/hub.go (sketch) 
type Hub struct {
  clients sync.Map // caseID → []*Client
}

func (h *Hub) Subscribe(caseID string) (*Client, func()) {
  ch := make(chan Event, 64)
  client := &Client{CaseID: caseID, Ch: ch}
  // Register and return unsubscribe func
  h.register(client)
  return client, func() { h.deregister(client) }
}

func (h *Hub) Publish(caseID string, evt Event) {
  if clients, ok := h.clients.Load(caseID); ok {
    for _, c := range clients.([]*Client) {
      select {
      case c.Ch <- evt: // non-blocking send
      default: // client buffer full → skip (client will replay on reconnect)
      }
    }
  }
}

// Emitter is the interface every module uses to emit timeline events.
// Accepts a *sql.Tx so the event INSERT is part of the caller's transaction.
type Emitter interface {
  Emit(ctx context.Context, tx *sql.Tx, event Event) error
}

type Event struct {
  CaseID     uuid.UUID
  EventType  EventType
  Source     Source
  ActorID    *uuid.UUID     // nil for system events
  OccurredAt time.Time     // real-world time, required
  Payload    map[string]any // serialized to JSONB
  Metadata   map[string]any
}

Performance

ConcernTargetApproach
Timeline load (first page) < 200ms P95 Composite index on (case_id, occurred_at DESC). 50-event page. No COUNT(*) on first load.
Large case (10,000+ events) Smooth scroll TanStack Virtual — only 20–30 DOM nodes rendered regardless of total event count.
SSE fan-out (100 clients, 1 case) < 5ms dispatch Go channel fan-out in hub.Publish. Buffered channel (64) prevents slow clients blocking fast path.
SSE connections per instance 500 concurrent Each SSE connection is a goroutine + channel. Go's goroutine scheduler handles this well.
Cursor pagination Stable ordering Cursor encodes (occurred_at, id) — breaks ties by UUID when timestamps collide (bulk imports).
PDF export (1000+ events) Async, < 30s River background job. Chrome headless rendering. Download via pre-signed S3 URL.
📌
Pagination Cursor Format
The opaque cursor is base64(JSON): {"occurred_at": "2025-12-08T09:14:22Z", "id": "550e8400..."}. The SQL WHERE clause becomes: WHERE (occurred_at, id) < ($1, $2) AND case_id = $3 AND deleted_at IS NULL ORDER BY occurred_at DESC, id DESC LIMIT $4. This leverages the composite index and produces deterministic, stable pages.

Test Strategy

Unit Tests
  • Event ordering: insert 50 events with scrambled occurred_at, verify GET returns them sorted newest-first
  • Cursor stability: page 2 cursor must not re-return events from page 1
  • Tie-breaking: two events with identical occurred_at ordered by UUID
  • Emitter mock: verify other modules (cases, tasks) call Emit with correct EventType and payload
SSE Integration Tests
  • Connect SSE client, emit event via domain service, assert event arrives on stream within 500ms
  • Disconnect and reconnect with Last-Event-ID, assert missed events are replayed in order
  • Heartbeat: assert ping event arrives within 35s window
  • Hub cleanup: after all clients disconnect, verify no goroutines remain (goleak)
Atomicity Tests
  • Simulate DB error mid-transaction: assert no timeline event was written when business op fails
  • Simulate Emit error: assert business op also rolls back (atomicity guarantee)
Frontend Tests
  • Vitest: EventCard renders correct variant for each of 18 event types
  • Playwright: load timeline with 500 events, assert virtualized list renders < 40 DOM nodes
  • Playwright: SSE mock, assert RealtimeIndicator shows "2 new events"

Why This Wins

Every enterprise investigation tool on the market — Salesforce Cases, Freshdesk, Jira, even specialized compliance tools like NICE Actimize — commits the same sin: they treat case data as a collection of records across tabs. Documents here, notes there, tasks over there, audit log buried in settings. Investigators must mentally assemble the chronology themselves, which is exactly the wrong thing to ask a human to do when they are under regulatory pressure, time constraints, and cognitive load.


The Timeline Workspace eliminates this entirely. Every atom of case activity — regardless of its type or origin, whether it was a document the system processed automatically at 3am or a phone call the analyst manually logged as having happened last Tuesday — appears in one ordered, readable, filterable stream. The investigator does not need to reconstruct the story. The story is already assembled.


This is not just a UX improvement. It is a regulatory advantage. When a compliance officer needs to show a regulator exactly what happened and when, they pull up one screen. The timeline is the case file. The audit report is a one-click export of the same view. No data munging. No "let me check the audit log separately." This is the insight that transforms OpsOwl AI from a case management tool into a true investigation platform.

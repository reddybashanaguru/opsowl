Case Management

The central entity of OpsOwl AI — structured investigation cases with lifecycle state machines, SLA tracking, intelligent assignment, and a complete activity trail for fintech and lending-ops teams.

⬡ Module 02 · Case Management
1
Feature Overview Core Entity

A Case in OpsOwl AI is the fundamental unit of work. It represents an investigation, compliance review, suspicious activity report, or operational exception that requires human analysis, collaboration, and resolution. Cases are how fintech operations teams — from fraud investigators to KYC analysts — track, assign, and close work items.

Every other OpsOwl AI feature — AI summaries, document attachments, audit trails, SLA alerts, escalations, and reporting — hangs off a case. Cases are immutable in their history: every state change, assignment, and edit is recorded. A case is never truly deleted — only soft-deleted, preserving the audit trail for regulatory inspection.

OWL-{YYYY}-{NNNNN}
Lifecycle States

Assign, status-change, tag (up to 100)

Cursor-based (UUID), max 100/page
📁
Regulatory Context: For NBFC and lending-ops teams, every case represents a potential regulatory touchpoint — a SAR (Suspicious Activity Report), a KYC exception, or a credit fraud investigation. Cases must be immutable in history, timestamped in UTC, and traceable to a named individual for regulatory examination. The Case Management module is designed with these constraints as first-class requirements.

Case Lifecycle State Machine

Cases follow a strict state machine. Transitions are validated server-side — invalid transitions return 422 Unprocessable Entity. State transitions are always recorded in the activity log with actor, timestamp, and optional reason.

draft
Creator saves
open
Published/submitted
in_progress
Analyst picks up
pending_review
Analyst submits
closed
escalated
→ Manager approves → closed → Manager rejects → back to in_progress → Escalated from any state → escalated → Escalated can be re-opened to in_progress

Role-to-Transition Permissions:

From State To State Allowed Roles Business Rule
draft open analyst, manager, admin Case must have title, description, and priority set
open in_progress analyst (self-assign), manager, admin Case must be assigned to a user
in_progress pending_review analyst (assigned only), manager, admin At least one activity entry must exist
pending_review closed manager, admin, super_admin Reviewer must not be the same user who submitted
pending_review in_progress manager, admin Rejection reason required (min 20 chars)
any (except closed) escalated manager, admin, super_admin Escalation reason required; notifies super_admin via SSE
escalated in_progress admin, super_admin Re-assignment mandatory on re-open

Database Schema PostgreSQL 18.4
-- ─────────────────────────────────────────────────────────────────
-- CASE MANAGEMENT SCHEMA — OpsOwl AI
-- PostgreSQL 18.4 | TIMESTAMPTZ | Soft deletes | UUID v4
-- ─────────────────────────────────────────────────────────────────

CREATE TYPE case_status AS ENUM (
  'draft', 'open', 'in_progress', 'pending_review', 'closed', 'escalated'
);
CREATE TYPE case_priority AS ENUM ('critical', 'high', 'medium', 'low');

-- cases ──────────────────────────────────────────────────────────
CREATE TABLE cases (
  id               UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
  case_number      TEXT          NOT NULL UNIQUE,             -- OWL-2026-00001
  title            TEXT          NOT NULL  CHECK(length(title) >= 5),
  description      TEXT          NOT NULL DEFAULT '',
  status           case_status   NOT NULL DEFAULT 'draft',
  priority         case_priority NOT NULL DEFAULT 'medium',
  assigned_to      UUID          REFERENCES users(id),         -- nullable
  created_by       UUID          NOT NULL REFERENCES users(id),
  organization_id  UUID          NOT NULL,                    -- multi-tenant scope
  due_date         TIMESTAMPTZ,                               -- optional manual override
  sla_breach_at    TIMESTAMPTZ,                               -- computed on creation
  sla_breached     BOOLEAN       NOT NULL DEFAULT FALSE,
  tags             TEXT[]        NOT NULL DEFAULT '{}',
  created_at       TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  updated_at       TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  deleted_at       TIMESTAMPTZ                                -- soft delete
);

-- Indexes
CREATE INDEX idx_cases_status         ON cases (status)          WHERE deleted_at IS NULL;
CREATE INDEX idx_cases_priority        ON cases (priority)        WHERE deleted_at IS NULL;
CREATE INDEX idx_cases_assigned_to     ON cases (assigned_to)     WHERE deleted_at IS NULL;
CREATE INDEX idx_cases_created_by      ON cases (created_by);
CREATE INDEX idx_cases_organization_id ON cases (organization_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_cases_sla_breach_at   ON cases (sla_breach_at)   WHERE deleted_at IS NULL AND sla_breached = FALSE;
CREATE INDEX idx_cases_created_at      ON cases (created_at       DESC);
CREATE INDEX idx_cases_tags            ON cases USING GIN (tags);

-- Sequence for case numbers per year
CREATE SEQUENCE case_number_seq START 1 INCREMENT 1 NO CYCLE;

-- case_assignments — full history of assignment changes ───────────
CREATE TABLE case_assignments (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  case_id     UUID        NOT NULL REFERENCES cases(id) ON DELETE CASCADE,
  assigned_to UUID        NOT NULL REFERENCES users(id),
  assigned_by UUID        NOT NULL REFERENCES users(id),
  assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  unassigned_at TIMESTAMPTZ                          -- set when next assignment happens
);

CREATE INDEX idx_ca_case_id     ON case_assignments (case_id);
CREATE INDEX idx_ca_assigned_to ON case_assignments (assigned_to);

-- case_tags — normalized tag registry ───────────────────────────
CREATE TABLE case_tags (
  id         UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  name       TEXT        NOT NULL UNIQUE,            -- lowercase, max 64 chars
  color_hex  CHAR(7)     NOT NULL DEFAULT '#64748b',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- case_watchers — users subscribed to case updates ───────────────
CREATE TABLE case_watchers (
  case_id    UUID        NOT NULL REFERENCES cases(id) ON DELETE CASCADE,
  user_id    UUID        NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (case_id, user_id)
);

CREATE INDEX idx_cw_user_id ON case_watchers (user_id);
4
Case Numbering

Each case receives a human-readable, unique, sequential identifier generated at creation time. It is stored as a TEXT column (not an integer) to preserve the formatted string.

OWL-2026-00001

Format: OWL-{YYYY}-{NNNNN}

  • ·OWL — fixed prefix, identifies OpsOwl AI system (useful in email subjects, audit reports)
  • ·{YYYY} — calendar year of case creation (resets to 00001 each January 1)
  • ·{NNNNN} — zero-padded 5-digit sequence; max 99,999 cases/year per organization
⚙
Generation Strategy: The case number is generated in a PostgreSQL function called within the INSERT transaction using a per-year sequence (case_number_seq). The function formats: FORMAT('OWL-%s-%05d', EXTRACT(YEAR FROM NOW()), nextval('case_number_seq')). The sequence is reset to 1 at year boundary via a River cron job that runs at 00:00:01 UTC on Jan 1. Multi-tenant orgs each have their own sequence.

1
SLA Computation on Case Creation
When a case moves from draft → open, sla_breach_at is set: created_at + SLA_HOURS[priority]. For Critical cases created at 14:00 IST: sla_breach_at = 18:00 IST. Non-working-hour adjustments are not applied in MVP (deferred to Phase 2 per product decision).
2
Breach Detection Job — River Cron, every 5 minutes
A River recurring job queries: SELECT id FROM cases WHERE sla_breach_at <= NOW() AND sla_breached = FALSE AND status NOT IN ('closed', 'escalated') AND deleted_at IS NULL. For each match: sets sla_breached = TRUE, writes a case.sla_breached audit event, and enqueues a notification job.
3
Notification Triggers on Breach
On sla_breached flagging: (a) SSE event pushed to assigned user's active browser session. (b) SSE event pushed to all watchers. (c) Manager and admin receive in-app notification. Email notification is a River job (Phase 2 integration with SendGrid). No SMS in MVP.
4
Priority Change Recalculation
If a manager upgrades a case's priority (e.g., medium → critical), sla_breach_at is recalculated as NOW() + SLA_HOURS[new_priority] and sla_breached is reset to FALSE. Old SLA window is recorded in the activity log for audit purposes.
5
SLA Pause on Closed / Escalated
SLA breach detection skips cases in closed or escalated states. Escalated cases have their own SLA clock managed separately (escalation SLA = Critical regardless of original priority). Closed cases are never re-evaluated for SLA.

UX Decisions
Decision Approach & Rationale
Bulk Operations Support bulk assign, status change, and tagging for up to 100 cases simultaneously. Ops teams routinely need to triage dozens of cases from a daily batch. BulkActionBar appears contextually — never clutters the UI when nothing is selected. Uses server-side batch endpoint (not N individual requests).
Keyboard Shortcuts N → New case, F → Focus filter bar, Esc → Close modals, J/K → Navigate case rows, Enter → Open case detail, A → Assign (on detail page), S → Change status (on detail page). Shortcuts are documented in a ? help modal.
Empty States Context-sensitive: no cases at all → "Create your first case" CTA; filtered with no results → "No cases match these filters" with clear-filter button; assigned_to=me with no cases → "No cases assigned to you — check your queue." Never a generic blank screen.
Mobile Responsiveness Breakpoint strategy: ≥1024px = full two-column layout. 768–1023px = single column, filter bar collapses to filter button + drawer. <768px = list-only view, no inline filters. Case detail on mobile: tabbed (Overview / Activity / Actions). Bulk operations disabled on mobile (<768px) — too error-prone on touch.
Optimistic Updates Status transitions and assignment changes apply optimistically to the UI before the API response. TanStack Query's onMutate + onError rollback pattern. SLA countdown recalculates client-side on priority change immediately, then corrects when server responds with computed sla_breach_at.
Real-Time Updates SSE endpoint at /api/v1/cases/:id/stream pushes activity events to all users viewing a case. TanStack Query's invalidateQueries triggered on SSE event receipt. No polling. SSE reconnects automatically with exponential backoff on connection drop.
URL-driven State All filter combinations serialized to URL searchParams. Users can bookmark a filtered view, share a URL with a colleague, or use browser back/forward to navigate filter history. Next.js router handles searchParams without a full page reload.

Audit Events

All case mutations and significant read events are written to the audit_logs table. Case activity events are additionally written to case_activity for the per-case timeline. The audit writer uses the same asynchronous buffered-channel worker as the auth module.

Event Code Trigger Key Fields Logged Severity
case.created New case created actor_id, case_id, case_number, priority, status info
case.updated Case fields edited actor_id, case_id, changed_fields[], old_values, new_values info
case.status_changed Status transition actor_id, case_id, from_status, to_status, reason info
case.escalated Case moved to escalated actor_id, case_id, from_status, escalation_reason warn
case.closed Case closed by reviewer actor_id, case_id, resolution_note, time_to_close_hours info
case.assigned Case assigned/reassigned actor_id, case_id, prev_assignee_id, new_assignee_id info
case.priority_changed Priority updated actor_id, case_id, old_priority, new_priority, new_sla_breach_at warn
case.sla_breached SLA breach detected by worker case_id, priority, breach_time, assigned_to_id, minutes_overdue warn
case.deleted Soft delete by admin actor_id, case_id, case_number, reason warn

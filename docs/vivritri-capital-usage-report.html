Issues Found During Evaluation

Issues encountered during hands-on use. Severity: 🔴 Critical (blocks work) · 🟠 High (significant friction) · 🟡 Medium (inconvenient) · 🟢 Resolved in current version

#1 RESOLVED ✓ AI Copilot Returns Internal Server Error

POST /cases/:id/ai/ask consistently returned {"code":"INTERNAL_ERROR"}. Unable to ask the copilot natural language questions about case facts — significant gap for analysts interrogating transaction patterns or drafting STR narratives in air-gapped mode.

✓ Fixed in v1.0.1: Embedding failures in the Python AI service are now caught and handled gracefully. The /ask, /generate-note, and /extract-actions endpoints return INSUFFICIENT_CONTEXT (not a 500 error) when the model is momentarily unavailable. Copilot Q&A confirmed fully operational with air-gapped Qwen2.5:7b post-patch.

#2 RESOLVED ✓ New Cases Default to "draft" Instead of "open"

Manually created cases (via POST /cases) started in "draft" status, meaning they did not appear in the open cases dashboard count or the analyst queue. Four Vivritri cases required a separate PATCH call to become visible.

✓ Fixed in v1.0.1: Service layer now creates all cases with status=open by default. New investigations are immediately visible in the analyst queue without any additional PATCH call. The draft→open transition path remains valid for any pre-existing draft cases.

#3 RESOLVED ✓ SLA Policies Don't Auto-Set Deadline on Case Creation

SLA policies were configured per priority tier (critical=168h) but the sla_breach_at field on newly created cases was null. The SLA clock only started when a deadline was manually set — unacceptable for RBI 7-day STR filing windows where the clock must start at case creation.

✓ Fixed in v1.0.1: sla_breach_at is now computed automatically at case creation using the priority-to-SLA mapping (critical=4h for immediate escalation, high=24h, medium=72h, low=7d). All new cases have an SLA breach timer from the moment they are created. No manual PATCH required.

#4 RESOLVED ✓ Full-Text Search Requires Indexing Warm-Up

Search endpoint (GET /search?q=structuring&filter=cases) returned 0 results despite 7 cases containing the term "structuring" in titles and descriptions. The tsvector search index was not populated synchronously with case creation, requiring a warm-up period before search returned results.

✓ Fixed in v1.0.1: ILIKE fallback added to the search service. When the tsvector index returns 0 results, the system automatically retries with case-insensitive pattern matching against case titles, descriptions, and case numbers. Search returns results immediately after data insertion — no warm-up required.

#5 RESOLVED ✓ Auto-Case Assignment Used Admin Queue Instead of Analyst

Previously, alert auto-converted cases landed in the admin queue regardless of the auto_assign_user_id field on the routing rule. This was fixed in the current release.

✓ Fixed: Assignment engine now uses (1) explicit auto_assign_user_id from rule, (2) workload-based fallback via assignment engine, (3) system user fallback. Verified in Case 1 auto-conversion.

#6 RESOLVED ✓ Auto-Converted Cases Had Generic "[TYPE] Name" Titles

Alert auto-conversion previously generated titles like "[STRUCTURING] Kiran Patel" with bracket notation. This looked unprofessional in the case queue.

✓ Fixed: formatAlertCaseTitle() now generates "Structuring Transaction – Kiran Patel (VIV-AC-7890123)" with title-case and em-dash format. Tests added.

#7 RESOLVED ✓ Docker Healthchecks Caused Container Instability

Ollama and Python AI service containers were showing "unhealthy" because curl/wget were not available in those container images. Services worked but deployment monitoring was broken.

✓ Fixed: Bash TCP check for Ollama, python3 urllib for AI service. Both containers now healthy.

#8 RESOLVED ✓ AI Analysis Not Triggered Automatically on Auto-Created Cases

Cases auto-created from alert ingestion did not trigger AI risk analysis. Analysts had to manually POST /insights/analyse for each case.

✓ Fixed: InsightsTrigger interface wired so TriggerAnalysis is called automatically after every auto-conversion. Integration tests confirm behavior.

#9 RESOLVED ✓ API Field Type Errors Returned Opaque Go Internals

Transaction and case creation endpoints returned Go's internal json.SyntaxError message when a field had the wrong type — e.g. passing a string where a float64 was expected for the "amount" field. The error gave no indication of which field was wrong or what type was expected, making scripting and integration painful.

✓ Fixed in v1.0.1: All endpoints now use a DecodeBody helper that detects json.UnmarshalTypeError and surfaces a field-specific message: field "amount" must be float64 (got string). Integration scripts for transaction bulk-loading now self-diagnose correctly.

#10 RESOLVED ✓ AI Narrative Generation Endpoint Missing Service Authentication

The /narrative/generate endpoint on the AI service accepted requests without validating the Authorization header. The Go narrative service also did not send the AI_SERVICE_SECRET header when calling the AI service, meaning the narrative endpoint was effectively unauthenticated — a security gap in any deployment where AI_SERVICE_SECRET is configured.

✓ Fixed in v1.0.1: The Go narrative service now sends Authorization: Bearer {AI_SERVICE_SECRET} on every AI call. The FastAPI /narrative/generate endpoint validates this token via the require_service_token dependency. Service-to-service auth is now consistent across all AI endpoints (copilot, documents, narrative).

📣 FEATURE · 09

Notifications

The async collaboration glue of OpsOwl AI. Investigators must know the moment they're assigned a case, when an SLA is about to breach, when someone @mentions them, or when AI processing completes — in real-time, without polling.

Go 1.26 River (job queue) SSE Resend PostgreSQL 18.4 Next.js 16 Zustand TanStack Query v5
01

Feature Overview

Notifications are the connective tissue of async investigation workflows. Without them, investigators must manually refresh dashboards, miss SLA deadlines, and lose context across distributed teams.

Why It Matters

  • Case assignment arrives instantly — no email delays
  • SLA breach warnings fire 2 hours early — time to act
  • @mentions surface the right investigator to the right thread
  • AI review requests route to humans immediately
  • Document processing completion closes the async loop

Design Principles

  • Real-time first — SSE for zero-latency in-app delivery
  • User-controlled — every type configurable per user
  • Non-invasive — intelligent grouping prevents fatigue
  • Async-safe — River jobs ensure no notification is lost
  • Multi-channel — in-app + email; Slack/Teams in Phase 2
ℹ

Architecture pattern: All notifications flow through a single notification.Service interface. Any Go module (cases, tasks, AI, documents) calls notif.Enqueue(ctx, NotificationJob{...}) which pushes a River job. The job handles fan-out to SSE + Resend. No module directly sends emails or writes to the SSE stream.

Notification Types Matrix

Eleven notification types cover the complete lifecycle of cases, tasks, AI operations, and documents. Each type has a defined trigger source, recipient set, and default channel configuration.

Case Notifications

CASE case_assigned HIGH PRIORITY
You were assigned as the primary investigator on a case.
Triggered by: Case create or reassign (cases module) · Recipients: Newly assigned investigator · In-App Email
CASE case_status_changed MEDIUM
A case you are watching has moved to a new status (e.g., Open → Under Review → Closed).
Triggered by: Status transition in cases module · Recipients: All case watchers (assigned investigator + explicit watchers) · In-App Email (configurable)
SLA case_sla_warning HIGH PRIORITY
A case SLA deadline is less than 2 hours away — action required immediately.
Triggered by: Scheduled River job (SLA monitor, runs every 15 min) · Recipients: Assigned investigator + team lead · In-App Email
SLA case_sla_breached CRITICAL
A case SLA has been breached. Escalation is automatic.
Triggered by: Scheduled River job (SLA monitor) · Recipients: Assigned investigator + team lead + admin · In-App Email (always-on)

Task Notifications

TASK task_assigned MEDIUM
A task within a case has been assigned to you.
Triggered by: Task create/reassign (tasks module) · Recipients: Task assignee · In-App Email (configurable)
TASK task_due_soon MEDIUM
A task assigned to you is due in less than 24 hours.
Triggered by: Scheduled River job (task due monitor, runs hourly) · Recipients: Task assignee · In-App Email (configurable)
TASK task_overdue HIGH PRIORITY
A task assigned to you has passed its due date without completion.
Triggered by: Scheduled River job (task due monitor) · Recipients: Task assignee + case investigator · In-App Email

Collaboration Notifications

COLLAB mention MEDIUM
Someone @mentioned you in a note, comment, or case update.
Triggered by: Note/comment created or edited (notes module, @mention parser) · Recipients: Mentioned users (parsed from content) · In-App Email

AI & Document Notifications

AI ai_review_required MEDIUM
The AI has completed analysis but its output requires human review before action.
Triggered by: AI module on low-confidence result · Recipients: Assigned investigator · In-App Email (configurable)
DOC document_processed LOW
A document you uploaded has been processed and its extracted data is available.
Triggered by: Document pipeline completion (documents module) · Recipients: Document uploader · In-App Email (configurable)
DOC document_failed HIGH PRIORITY
Document processing failed — the uploader must re-upload or investigate the failure.
Triggered by: Document pipeline failure (documents module) · Recipients: Document uploader · In-App Email
03

Delivery Channels

In-App (SSE)

ALWAYS ON

Server-Sent Events stream per authenticated session. Zero-latency push. No polling. Client reconnects on disconnect with Last-Event-ID to replay missed events.

GET /api/v1/notifications/stream

Email (Resend)

CONFIGURABLE

Transactional emails via Resend SDK. Per-user, per-type toggle in preferences. HTML templates embedded in Go binary via embed.FS. Sent from alerts@opsowl.ai.

Resend Go SDK

Slack / Teams

PHASE 2

Webhook-based delivery to Slack channels and Microsoft Teams. Architecture is designed to support additional channels via the NotificationSender interface without schema changes.

Deferred
⚠

SLA breached notifications bypass user preferences and are always delivered via both in-app and email — this cannot be disabled. Regulatory context requires guaranteed delivery for SLA breach events.

Database Schema

Two tables: notifications stores each notification instance; notification_preferences stores per-user channel configuration per type.

-- ─────────────────────────────────────────────────────────
-- Enum: notification_type
-- ─────────────────────────────────────────────────────────
CREATE TYPE notification_type AS ENUM (
    'case_assigned',
    'case_status_changed',
    'case_sla_warning',
    'case_sla_breached',
    'task_assigned',
    'task_due_soon',
    'task_overdue',
    'mention',
    'ai_review_required',
    'document_processed',
    'document_failed'
);

-- ─────────────────────────────────────────────────────────
-- Table: notifications
-- ─────────────────────────────────────────────────────────
CREATE TABLE notifications (
    id             UUID                     PRIMARY KEY DEFAULT gen_random_uuid(),
    recipient_id   UUID                     NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type           notification_type        NOT NULL,
    title          TEXT                     NOT NULL,
    message        TEXT                     NOT NULL,
    link_url       TEXT,                    -- deep link: /cases/:id, /tasks/:id, etc.
    is_read        BOOLEAN                  NOT NULL DEFAULT FALSE,
    read_at        TIMESTAMPTZ,
    case_id        UUID                     REFERENCES cases(id) ON DELETE SET NULL,
    task_id        UUID                     REFERENCES tasks(id) ON DELETE SET NULL,
    created_at     TIMESTAMPTZ              NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ              NOT NULL DEFAULT NOW()
);

-- Indexes
CREATE INDEX idx_notifications_recipient_unread
    ON notifications (recipient_id, is_read, created_at DESC);

CREATE INDEX idx_notifications_recipient_created
    ON notifications (recipient_id, created_at DESC);

CREATE INDEX idx_notifications_case
    ON notifications (case_id) WHERE case_id IS NOT NULL;

-- ─────────────────────────────────────────────────────────
-- Table: notification_preferences
-- ─────────────────────────────────────────────────────────
CREATE TABLE notification_preferences (
    id                UUID               PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id           UUID               NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    notification_type notification_type  NOT NULL,
    in_app_enabled    BOOLEAN            NOT NULL DEFAULT TRUE,
    email_enabled     BOOLEAN            NOT NULL DEFAULT TRUE,
    created_at        TIMESTAMPTZ        NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ        NOT NULL DEFAULT NOW(),
    UNIQUE (user_id, notification_type)
);

-- Index for fast preference lookup on notification send
CREATE INDEX idx_notification_prefs_user
    ON notification_preferences (user_id);

-- Trigger: auto-update updated_at
CREATE TRIGGER set_notification_preferences_updated_at
    BEFORE UPDATE ON notification_preferences
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
ℹ

Default preferences: Rows are created on-demand when a user first customises a preference. If no row exists, the system defaults to in_app=true, email=true for all types. This avoids pre-populating 11 rows per user on account creation.

Notification Triggers

Every notification originates from a system event. The mapping below shows the complete chain from event → notification type → River job → recipient set.

System Event Notification Type River Job Recipients Trigger Mechanism
Case created / reassigned case_assigned NotificationJob New assignee cases.Service after DB write
Case status transition case_status_changed NotificationJob Watchers list cases.Service on UpdateStatus
SLA < 2 hours case_sla_warning SLAMonitorJob Assignee + team lead Cron: every 15 min
SLA deadline passed case_sla_breached SLAMonitorJob Assignee + lead + admin Cron: every 15 min
Task created / reassigned task_assigned NotificationJob Task assignee tasks.Service after DB write
Task due in < 24h task_due_soon TaskDueMonitorJob Task assignee Cron: hourly
Task due date passed task_overdue TaskDueMonitorJob Assignee + investigator Cron: hourly
@mention in note/comment mention NotificationJob Mentioned users notes.Service, @mention parser
AI result low-confidence ai_review_required NotificationJob Assigned investigator ai.Service on completion
Document pipeline done document_processed NotificationJob Uploader documents.Service on success
Document pipeline error document_failed NotificationJob Uploader documents.Service on failure
ℹ

Idempotency: Scheduled jobs (SLA monitor, task due monitor) use a GROUP BY query to find cases/tasks in the relevant state. Before enqueueing, they check if a notification of that type was already sent within the last N hours using a DISTINCT ON (case_id, type) guard query — preventing duplicate SLA warnings on every cron tick.

River Job Design

All notification delivery is handled asynchronously through River — a Postgres-backed job queue. This guarantees at-least-once delivery even if the server restarts mid-request.

// internal/notification/jobs.go

package notification

// NotificationJobArgs is the River job payload for a single notification event.
// All fields needed to create DB rows and send emails are included here
// so the job is fully self-contained — no additional DB reads required.
type NotificationJobArgs struct {
    RecipientIDs  []string `json:"recipient_ids"`
    Type          string   `json:"type"`
    Title         string   `json:"title"`
    Message       string   `json:"message"`
    LinkURL       string   `json:"link_url,omitempty"`
    CaseID        string   `json:"case_id,omitempty"`
    TaskID        string   `json:"task_id,omitempty"`
    ActorName     string   `json:"actor_name,omitempty"`  // for personalised messages
}

// Kind returns the River job kind string (used for routing to the correct worker).
func (NotificationJobArgs) Kind() string { return "notification" }

// ─────────────────────────────────────────────────────────
// internal/notification/worker.go

type NotificationWorker struct {
    river.WorkerDefaults[NotificationJobArgs]
    db     *pgxpool.Pool
    resend *resend.Client
    sse    *SSEHub
    prefs  PreferenceStore
    tmpl   *template.Template  // embedded Go email templates
}

func (w *NotificationWorker) Work(ctx context.Context, job *river.Job[NotificationJobArgs]) error {
    args := job.Args

    for _, recipientID := range args.RecipientIDs {
        // 1. Load user preferences
        pref, _ := w.prefs.Get(ctx, recipientID, args.Type)

        // 2. Write notification row to DB (always)
        notifID, err := w.insertNotification(ctx, recipientID, args)
        if err != nil { return err }

        // 3. Push via SSE if user has an active session and in-app is enabled
        if pref.InAppEnabled {
            w.sse.Publish(recipientID, SSEEvent{
                ID:   notifID,
                Type: args.Type,
                Data: args,
            })
        }

        // 4. Send email if enabled (or if SLA breached — always send)
        alwaysSendEmail := args.Type == "case_sla_breached"
        if pref.EmailEnabled || alwaysSendEmail {
            if err := w.sendEmail(ctx, recipientID, args); err != nil {
                // Log but don't fail the job — SSE already delivered
                w.log.Error("email send failed", zap.Error(err))
            }
        }
    }
    return nil
}

River Job Configuration

  • Queue: notifications (dedicated queue)
  • Concurrency: 10 workers
  • Max attempts: 5
  • Backoff: Exponential with jitter

Enqueue Pattern

  • Any module calls notification.Service.Enqueue()
  • Service validates args and calls riverClient.Insert()
  • River persists job atomically in same Postgres transaction
  • Worker picks up job and executes delivery

Resend Integration

func (w *NotificationWorker) sendEmail(
    ctx context.Context,
    recipientID string,
    args NotificationJobArgs,
) error {
    user, _ := w.getUser(ctx, recipientID)

    // Render HTML from embedded template
    htmlBody, _ := w.renderTemplate(args.Type, EmailData{
        RecipientName: user.FullName,
        Title:         args.Title,
        Message:       args.Message,
        ActionURL:     buildDeepLink(args.LinkURL),
        Year:          time.Now().Year(),
    })

    _, err := w.resend.Emails.Send(&resend.SendEmailRequest{
        From:    "OpsOwl Alerts <alerts@opsowl.ai>",
        To:      []string{user.Email},
        Subject: args.Title,
        Html:    htmlBody,
        Tags: []resend.Tag{
            {Name: "type", Value: args.Type},
        },
    })
    return err
}

SSE Delivery (In-App Real-Time)

Server-Sent Events provides a persistent, one-way HTTP connection from server to browser. Each authenticated user gets a dedicated SSE stream. Notifications are pushed immediately when the River job executes.

SSE Hub Architecture

// internal/notification/sse.go

type SSEHub struct {
    mu      sync.RWMutex
    clients map[string][]chan SSEEvent  // userID → []channels (multi-tab support)
}

// Publish sends an event to ALL active sessions for a user.
func (h *SSEHub) Publish(userID string, event SSEEvent) {
    h.mu.RLock()
    defer h.mu.RUnlock()
    for _, ch := range h.clients[userID] {
        select {
        case ch <- event:
        default: // client buffer full — skip (client will catch up via poll)
        }
    }
}

// SSEHandler handles GET /api/v1/notifications/stream
func (h *SSEHub) SSEHandler(w http.ResponseWriter, r *http.Request) {
    userID := userIDFromCtx(r.Context())

    // SSE headers
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    w.Header().Set("X-Accel-Buffering", "no")  // disable Nginx buffering

    ch := h.subscribe(userID)
    defer h.unsubscribe(userID, ch)

    flusher := w.(http.Flusher)

    // Send ping every 30s to keep connection alive through proxies
    ticker := time.NewTicker(30 * time.Second)
    defer ticker.Stop()

    for {
        select {
        case event := <-ch:
            fmt.Fprintf(w, "id: %s\nevent: %s\ndata: %s\n\n",
                event.ID, event.Type, mustJSON(event.Data))
            flusher.Flush()
        case <-ticker.C:
            fmt.Fprintf(w, ": ping\n\n")
            flusher.Flush()
        case <-r.Context().Done():
            return
        }
    }
}

Client-Side (Next.js)

// hooks/useNotificationStream.ts
const useNotificationStream = () => {
  useEffect(() => {
    const es = new EventSource(
      '/api/v1/notifications/stream',
      { withCredentials: true }
    );
    es.addEventListener('notification', (e) => {

    });
    return () => es.close();
  }, []);
};

Reconnect Strategy

  • Browser automatically reconnects on disconnect
  • Client sends Last-Event-ID header on reconnect
  • Server replays notifications created after that ID
  • Multi-tab: each tab opens its own SSE connection
  • SSEHub supports N connections per userID

API Endpoints

All endpoints follow the {data, meta, error} envelope. Pagination uses cursor-based strategy. All timestamps are ISO 8601 UTC.

GET /api/v1/notifications Paginated notification list. Query: ?unread_only=true&cursor=&limit=20
PUT /api/v1/notifications/:id/read Mark a single notification as read. Sets is_read=true, read_at=NOW()
PUT /api/v1/notifications/read-all Mark all unread notifications as read for the authenticated user
GET /api/v1/notifications/count Returns {"data":{"unread_count":5}} — used for bell badge. Cheap query
GET /api/v1/notifications/stream SSE stream. Returns text/event-stream. Auth required. Persistent connection
GET /api/v1/notification-preferences Returns all preference settings for the authenticated user (defaults if not set)
PUT /api/v1/notification-preferences Upsert preferences. Body: [{type, in_app_enabled, email_enabled}]

Notification Grouping

When multiple similar notifications fire rapidly (e.g., 8 comments on the same case), displaying them individually creates notification fatigue. Grouping collapses them into a single actionable summary.

Grouping Rules

Scenario Individual Grouped (after 3+) Grouping Window
Multiple @mentions, same case "Priya mentioned you" "5 new mentions in Case OWL-2026-00042" 15 minutes
Multiple task assignments "Task X assigned to you" "3 tasks assigned to you" 5 minutes
Document batch processing "kyc_form.pdf processed" "4 documents processed successfully" 10 minutes

Implementation

The NotificationWorker checks a Redis-backed GroupingBuffer (key: notif:group:{userID}:{type}:{resourceID}, TTL = window). If buffer count >= 3, it upserts a grouped notification row rather than inserting a new one.

SLA Exceptions

SLA warning and breach notifications are never grouped. Each case gets its own notification row regardless of how many cases breach simultaneously. Safety-critical events require individual visibility.

Test Strategy

River Job Delivery Tests

  • Unit test NotificationWorker.Work() with mock DB, SSE hub, and Resend client
  • Verify correct notification type → correct template selected
  • Test preference-gating: email suppressed when email_enabled=false
  • Test SLA breach bypasses preference gating
  • Integration test: enqueue River job in test Postgres, verify notification row inserted
  • Test idempotency: duplicate SLA warning jobs should not create duplicate rows

SSE Push Tests

  • Unit test SSEHub.Publish() fan-out to multiple channels for same user
  • Test graceful handling of full client buffer (non-blocking send)
  • Test subscribe/unsubscribe lifecycle (no goroutine leaks)
  • Integration test: HTTP test server, connect SSE client, trigger notification, assert event received within 500ms
  • Test ping event is sent every 30s

Email Template Tests

  • Render all 10 email templates with sample data — assert no template errors
  • Assert required fields present in rendered HTML (title, CTA link, recipient name)
  • Validate HTML structure (no unclosed tags) using golang.org/x/net/html
  • Snapshot test to catch unintentional template regressions

API Endpoint Tests

  • Test GET /notifications pagination: cursor-based, correct ordering
  • Test PUT /notifications/:id/read — 404 on non-existent, 403 on other user's notification
  • Test GET /notifications/count accuracy after mark-read operations
  • Test PUT /notification-preferences upsert logic (create + update)

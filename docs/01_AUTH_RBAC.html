Authentication & Role-Based Access Control

Secure, auditable identity management for enterprise fintech operations teams — JWT RS256, refresh token rotation, and granular role-based permissions.

⬡ Module 01 · Auth & RBAC
1
Feature Overview Core Trust Layer

The Authentication & RBAC module is the security foundation of OpsOwl AI. Every request entering the system must carry a cryptographically verified identity, and every action must be authorized against a well-defined permission set. In regulated fintech and lending-ops environments, a breach of access control is not just a technical failure — it is a compliance incident.

This module governs: who can log in, what they can see and do, how long their session lasts, and what gets written to the audit trail. It provides the identity context consumed by every other OpsOwl AI module downstream.

🔐
Enterprise Trust Requirement: Fintech and NBFC customers operate under RBI, SEBI, and internal compliance mandates. Authentication failures, privilege escalation, and missing audit trails are direct audit findings. Every design decision here prioritizes auditability and least-privilege access.

Roles & Permissions Matrix

Five roles form a hierarchical permission structure. Roles are stored as a PostgreSQL ENUM on the users table. A user has exactly one role. Field-level permissions are enforced in the API response serialization layer — certain fields (e.g., password_hash, PII fields marked sensitive) are stripped based on caller role.

Role CRUD Cases Assign Tasks Manage Users View Audit Logs Access AI System Config Delete Records
super_admin Full Full Full Full Full Full Full
admin Full Full Org scope Full Full Read only Soft delete
manager Full Full View only Org scope Full No No
analyst Own + assigned Own cases No Own actions Full No No
viewer Read only No No No View results No No
⚡
Field-Level Permissions: Sensitive fields (e.g., password_hash, ssn_last4, internal notes marked confidential) are excluded from API responses unless the caller holds admin or super_admin. Enforced in sqlc query result mappers before serialization. No field reaches a lower-privilege user by accident.

Database Schema PostgreSQL 18.4

All tables follow the OpsOwl DB rules: UUID v4 primary keys, TIMESTAMPTZ for all datetime fields, soft deletes via deleted_at, and indexes on every FK and column used in WHERE/ORDER BY clauses. No raw SQL — all queries generated via sqlc.

-- ─────────────────────────────────────────────────────────────────
-- AUTH SCHEMA — OpsOwl AI
-- PostgreSQL 18.4 | All times UTC | Soft deletes via deleted_at
-- ─────────────────────────────────────────────────────────────────

CREATE TYPE user_role AS ENUM (
  'super_admin', 'admin', 'manager', 'analyst', 'viewer'
);

-- users ──────────────────────────────────────────────────────────
CREATE TABLE users (
  id              UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  email           TEXT        NOT NULL UNIQUE,
  password_hash   TEXT        NOT NULL,               -- bcrypt cost 12
  full_name       TEXT        NOT NULL,
  role            user_role   NOT NULL DEFAULT 'analyst',
  is_active       BOOLEAN     NOT NULL DEFAULT TRUE,
  last_login_at   TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  deleted_at      TIMESTAMPTZ                          -- soft delete
);

CREATE INDEX idx_users_email        ON users (email)        WHERE deleted_at IS NULL;
CREATE INDEX idx_users_role         ON users (role)         WHERE deleted_at IS NULL;
CREATE INDEX idx_users_is_active    ON users (is_active)    WHERE deleted_at IS NULL;
CREATE INDEX idx_users_created_at   ON users (created_at);

-- refresh_tokens ────────────────────────────────────────────────
CREATE TABLE refresh_tokens (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  TEXT        NOT NULL UNIQUE,              -- SHA-256 of raw token
  expires_at  TIMESTAMPTZ NOT NULL,
  revoked_at  TIMESTAMPTZ,                              -- NULL = active
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_rt_user_id    ON refresh_tokens (user_id);
CREATE INDEX idx_rt_expires_at ON refresh_tokens (expires_at);
CREATE INDEX idx_rt_hash       ON refresh_tokens (token_hash) WHERE revoked_at IS NULL;

-- sessions ───────────────────────────────────────────────────────
CREATE TABLE sessions (
  id              UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  ip_address      INET        NOT NULL,
  user_agent      TEXT        NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_active_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_sessions_user_id       ON sessions (user_id);
CREATE INDEX idx_sessions_last_active   ON sessions (last_active_at);
⚠
Token Hash Storage: Raw refresh tokens are never persisted. Only a SHA-256 hash of the token is stored in refresh_tokens.token_hash. The raw token is returned to the client once and never re-derivable from the DB — preventing insider token theft.

Middleware Design

All protected routes pass through a three-layer middleware chain in Chi router. Middlewares are composable and testable in isolation.

🔑
JWTValidate Middleware
Extracts Authorization: Bearer <token> header. Verifies RS256 signature using public key. Checks exp, iss, aud claims. On success, injects Claims{UserID, Role, Email} into context.Context. Returns 401 on any failure — no user identity reaches downstream handlers without a valid JWT.
↓
🛡
RBAC Middleware — RequireRole(roles ...UserRole)
Factory function wrapping any handler. Reads Claims from context. Checks if claims.Role is in the allowed set. Returns 403 if insufficient. Also enforces ownership checks for analyst role — e.g., analyst can only access cases assigned to them. Field-level stripping happens in the response serializer, not here.
↓
📋
AuditIntercept Middleware
Wraps http.ResponseWriter to capture status code. After handler returns, writes an audit event: user_id, action (derived from method+path), resource_type, resource_id, ip_address, status_code, timestamp. Uses non-blocking channel write to audit worker to avoid adding latency to hot paths.
⚙
Rate Limit Middleware sits at the outermost layer (before JWT validation) and uses an in-process token bucket keyed by IP for unauthenticated routes, and by user_id for authenticated routes. Limit: 100 req/min. Returns 429 Too Many Requests with Retry-After header.

Security Decisions
Decision Rationale
RS256 over HS256 Asymmetric signing allows the AI service and future microservices to verify tokens without holding the signing key. Only the Go auth service holds the private key. Public key is distributed via JWKS endpoint. A compromised consumer service cannot forge tokens.
bcrypt cost 12 Cost 12 takes ~250ms on modern hardware — fast enough for login UX but computationally expensive for bulk brute-force. Below 10 is considered weak; above 14 adds unacceptable login latency. 12 is the industry-standard sweet spot for 2026 hardware.
Refresh token rotation Every use of a refresh token issues a new pair (access + refresh) and revokes the old. If an attacker steals a refresh token, the legitimate user's next request will detect a double-use and trigger family revocation — all tokens for that user are invalidated.
Hash-only token storage Storing SHA-256(token) means a DB breach exposes no usable tokens. Brute-forcing 256-bit hashes is computationally infeasible. No rainbow table attack is possible since the token contains sufficient entropy (128 bits random).
HttpOnly cookie + body Refresh token returned both in response body (for native/mobile clients) and as an HttpOnly; Secure; SameSite=Strict cookie (for browser clients). XSS cannot steal the HttpOnly cookie. The body return is omitted for browser-originated requests (detected via X-Requested-With).
Short access token lifetime (1hr) Reduces the window of stolen JWT exploitation. JWTs cannot be individually revoked without DB lookups — short lifetime limits blast radius. Critical actions (delete user, role change) additionally verify the user's session recency.

useAuth hook
lib/hooks/useAuth.ts
  • Reads auth state from Zustand store
  • Exposes: user, isAuthenticated, logout(), hasRole()
  • Auto-refresh: sets up interval at 55min to call /auth/refresh
  • On 401 from any API call → triggers refresh flow via axios interceptor
  • On refresh failure → clears state, redirect to /login
authStore
lib/stores/auth.store.ts
  • Zustand store: { user, accessToken, setAuth, clearAuth }
  • Access token stored in memory only (no localStorage — XSS safe)
  • Persists user metadata to sessionStorage for page-reload resilience
  • Provides selector: selectUserRole for RBAC gate
ProtectedRoute
components/auth/ProtectedRoute.tsx
  • Wraps layout — checks isAuthenticated from authStore
  • Redirects to /login with returnUrl param if unauthenticated
  • Shows loading skeleton during auth hydration
  • Used in app/(dashboard)/layout.tsx
RBACGate
components/auth/RBACGate.tsx
  • Props: allowedRoles, fallback (optional)

Test Strategy >90% Coverage Target
🧪
Approach: Table-driven Go tests with testcontainers-go for real PostgreSQL. No mocked DB — integration tests run against an ephemeral pg container. HTTP handler tests use httptest.NewRecorder. Coverage checked with go test -coverprofile in CI. Target: >90% line coverage on auth and users packages.
  • ✓

  • ✓
    Login: wrong password → 401, no token issued, failed_login audit event written
  • ✓

  • ✓

  • ✓
    Refresh: valid RT → new JWT + new RT, old RT revoked_at set
  • ✓

  • ✓

  • ✓

  • ✓

  • ✓

  • ✓

  • ✓
    Password change: success → all existing refresh tokens revoked
  • ✓

  • ✓

  • ✓

Audit Events

All auth events are written to the audit_logs table (defined in the Audit module). The auth middleware writes these asynchronously via a buffered channel worker to keep hot-path latency unaffected.

Event Code Trigger Key Fields Logged Severity
auth.login.success Successful login user_id, ip_address, user_agent, session_id info
auth.login.failed Wrong password or unknown email email (attempted), ip_address, attempt_count warn
auth.login.account_disabled Login attempt on deactivated account user_id, ip_address warn
auth.logout Explicit logout user_id, session_id, ip_address info
auth.token.refresh Successful token refresh user_id, old_rt_id, new_rt_id info
auth.token.reuse_detected Revoked refresh token presented user_id, ip_address, rt_hash critical
auth.password.changed Successful password change user_id, ip_address, tokens_revoked_count info
user.created Admin creates new user actor_user_id, new_user_id, role, email info
user.role_changed Admin changes user role actor_user_id, target_user_id, old_role, new_role warn
user.deactivated Admin soft-deletes user actor_user_id, target_user_id warn
auth.rate_limit.hit User exceeds 100 req/min user_id or ip_address, endpoint, request_count warn

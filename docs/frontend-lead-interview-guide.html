1. React Core Concepts

Virtual DOM & Reconciliation

React maintains an in-memory Virtual DOM (a lightweight JS object tree). On each render it diffs the new tree against the previous one (reconciliation) and applies only the minimum set of real DOM mutations.

Key insight
React Fiber (React 16+) is the reconciler engine. It breaks reconciliation into units of work that can be paused, prioritised, and resumed — enabling concurrent features like Suspense and useTransition. Each fiber node corresponds to one component instance and holds state, effects, and a pointer to the next fiber.
Why is mutating state directly wrong in React?
React's change detection is based on referential equality. When you call setState or a Zustand setter, React compares the new value with the old reference. If you mutate in place (e.g. arr.push(x) then set the same reference), the reference hasn't changed, so React sees "no update" and skips re-render. Always create new objects/arrays: setState([...arr, x]).

useState vs useReducer

Use useState for independent, simple values. Switch to useReducer when state transitions are complex or multiple sub-values update together:

type Action = { type: "set_loading" } | { type: "set_data"; data: Case[] } | { type: "set_error"; err: string };

  switch (action.type) {

    case "set_error":   return { ...state, loading: false, error: action.err };

useEffect — Dependency Array Rules

Common interview trap
Every reactive value used inside useEffect must be in the dependency array — or you risk stale closures. The ESLint rule exhaustive-deps enforces this. To break a dependency cycle, move the value into a useRef (see onEventRef in useTimelineSSE below).

useMemo vs useCallback

HookReturnsUse when
useMemo(fn, deps)The computed valueExpensive computation; passing object/array as prop to memoized child
useCallback(fn, deps)A stable function referencePassing callbacks to memoized children; useEffect dependency that is a function
OpsOwl — useTimelineSSE.ts

The connect function is wrapped in useCallback with [caseId, enabled] deps so the useEffect that calls it doesn't re-fire on every render. The onEvent callback is stored in onEventRef.current (a ref) so it can be called inside the EventSource handler without being a dependency — breaking what would be an infinite loop.

useRef — Three Use Cases

  1. DOM access — const inputRef = useRef<HTMLInputElement>(null)
  2. Mutable value that doesn't trigger re-render — timers, counters, EventSource references
  3. Stable callback reference — store latest prop/callback in a ref so stale closures don't capture old values
OpsOwl — useTimelineSSE.ts (lines 35–36)

onEventRef.current = onEvent — the latest onEvent prop is always written to the ref synchronously each render. The EventSource handler reads onEventRef.current?.(event). This means the handler never goes stale, yet it doesn't need to be listed as a useCallback dependency.

useContext — Performance Pitfall

Every consumer re-renders when any part of the context value changes. Mitigations:

  • Split contexts by update frequency (user context vs theme context)
  • Use a state management library (Zustand) for frequently-changing global state
  • Wrap the Provider's value in useMemo
When would you use context over Zustand?
Context is good for static or rarely-changing values (theme, locale, feature flags). Zustand is better for frequently-changing shared state (auth user, case filters, notification count) because Zustand uses a subscription model — only components that subscribe to a specific slice re-render. In OpsOwl we use Zustand for authStore and configStore, while TanStack Query handles all server state.

useIdleTimeout — Timer management hook

// apps/web/src/lib/hooks/useIdleTimeout.ts
// Detects user inactivity and fires onTimeout after IDLE_TIMEOUT_MS.
// Shows a 2-minute warning countdown before logout.

const IDLE_TIMEOUT_MS = (Number(process.env.NEXT_PUBLIC_IDLE_TIMEOUT_MINUTES) || 15) * 60_000;
const ACTIVITY_EVENTS = ["mousemove", "mousedown", "keydown", "touchstart", "click"] as const;

export function useIdleTimeout({ onTimeout, enabled = true }: Options) {
  const [warningVisible, setWarningVisible] = useState(false);
  const [secondsLeft, setSecondsLeft] = useState(120);
  const logoutTimer  = useRef<ReturnType<typeof setTimeout> | null>(null);
  const onTimeoutRef = useRef(onTimeout);
  onTimeoutRef.current = onTimeout; // always latest

  const resetTimers = useCallback(() => {
    // ... schedule warning + logout timers
    logoutTimer.current = setTimeout(() => onTimeoutRef.current(), IDLE_TIMEOUT_MS);
  }, []);

  useEffect(() => {
    if (!enabled) { clearAll(); return; }
    resetTimers();
    const handler = () => resetTimers();
    ACTIVITY_EVENTS.forEach(e => window.addEventListener(e, handler, { passive: true }));
    return () => ACTIVITY_EVENTS.forEach(e => window.removeEventListener(e, handler));
  }, [enabled, resetTimers]);

  return { warningVisible, secondsLeft, extendSession: resetTimers };
}
Interview answer
When asked "how do you handle session expiry?" — describe this exact pattern: idle timer on activity events, 2-min warning countdown, logout fires clearAuth() + redirects with returnUrl so the user lands back on the same page after re-login.

useTimelineSSE — Real-time event streaming hook

// Key features of the SSE hook:
// 1. Gets a short-lived ticket (90s) from /api/v1/auth/sse-ticket — avoids
//    putting the full access_token in the URL (EventSource can't set headers).
// 2. Sends ?last_event_id= on reconnect so no events are missed.
// 3. Exponential backoff: 1s → 2s → 4s … capped at 30s.
// 4. Closes EventSource on onerror immediately — prevents browser auto-retry
//    with a stale token.
// 5. Cleanup on unmount: close ES + cancel pending reconnect timer.

const connect = useCallback(async () => {
  const token = await getSseTicket();           // short-lived ticket
  const url = new URL(`${BASE_URL}/api/v1/cases/${caseId}/timeline/stream`);
  url.searchParams.set("token", token);
  if (lastEventId.current) url.searchParams.set("last_event_id", lastEventId.current);

  const es = new EventSource(url.toString());
  es.addEventListener("timeline_event", (e: MessageEvent) => {
    const event = JSON.parse(e.data) as TimelineEvent;
    if (e.lastEventId) lastEventId.current = e.lastEventId;
    onEventRef.current?.(event);
  });
  es.onerror = () => {
    es.close();                                   // prevent browser auto-retry
    reconnectTimer.current = setTimeout(() => {
      reconnectDelay.current = Math.min(reconnectDelay.current * 2, MAX_RECONNECT_DELAY_MS);
      connect();
    }, reconnectDelay.current);
  };
}, [caseId, enabled]);

4. React Performance Optimization

Memoization Hierarchy

  1. React.memo(Component) — prevents re-render if props haven't changed (shallow comparison)
  2. useMemo(fn, deps) — memoize expensive derived values
  3. useCallback(fn, deps) — stable function reference for memo'd children
Don't over-memoize
Memoization has a cost (comparison on every render). Only apply it when: (1) the computation is measurably slow, (2) a child wrapped in React.memo would re-render unnecessarily, or (3) a function is used as a useEffect dependency.

  const obs = new IntersectionObserver(([entry]) => {
    if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) fetchNextPage();

Why cursor pagination over offset?
Offset pagination (LIMIT 25 OFFSET 50) is slow on large tables and produces duplicates if rows are inserted mid-scroll. Cursor pagination (WHERE id > cursor ORDER BY id LIMIT 25) is O(log n) on an indexed column and is stable under concurrent inserts.

List Virtualization

For lists with 1000+ rows, render only visible items using a virtual window. Libraries: @tanstack/react-virtual, react-window. In OpsOwl the cases list uses infinite scroll (25 items per page) which avoids the need for virtualization in practice.

What are Core Web Vitals and how do you improve them?
LCP (Largest Contentful Paint) — time until the largest image/text block is visible. Improve: preload hero images, use next/image with priority, reduce TTFB with CDN/caching.

INP (Interaction to Next Paint) — responsiveness to user input. Improve: break up long tasks with useTransition, avoid synchronous layout reads in event handlers, defer non-critical work with requestIdleCallback.

CLS (Cumulative Layout Shift) — unexpected layout shifts. Improve: always set explicit width/height on images, avoid injecting content above existing content, use CSS transforms for animations (not top/left).

SSE Token Problem

Why SSE needs a separate ticket
EventSource cannot set custom headers — it uses GET with browser-managed cookies. If the same-site policy allows cookies (which it does for same-origin), the access_token cookie is sent automatically. But if you need to authenticate cross-origin SSE (e.g., Next.js frontend on :3001 talking to Go API on :8080), cookies won't be sent. OpsOwl solves this by issuing a short-lived (90s) SSE ticket via a cookie-authenticated endpoint, then appending it as ?token= in the URL.

11. Role-Based Access Control (RBAC)

Three-layer RBAC in OpsOwl

  1. Zustand store — hasRole(): hierarchical check — admin can do anything manager can do
  2. <RBACGate> component: wraps UI sections that should only show for certain roles
  3. Backend enforcement: every API endpoint checks the JWT role claim — frontend gates are UX-only
// RBACGate — gate entire sections of UI
<RBACGate allowedRoles={["admin", "super_admin"]}>
  <AdminNavSection />
</RBACGate>

// Programmatic check — gate individual actions
const { hasRole } = useAuth();
const canEscalate = hasRole("manager", "admin", "super_admin");

// hasRole uses hierarchy: passing "manager" allows manager, admin, super_admin
function hasRole(...roles: UserRole[]) {
  const userLevel = ROLE_HIERARCHY[user.role];
  return roles.some(r => ROLE_HIERARCHY[r] <= userLevel);
  // manager(3) <= admin(4) → admin CAN do manager actions ✓
}
What's the difference between authentication and authorization?
Authentication = "who are you?" — verifying identity via JWT/session. Authorization = "what can you do?" — checking permissions after identity is confirmed. In OpsOwl: the JWT cookie proves identity (auth); the role claim inside the JWT determines what routes/actions are permitted (authz).

12. Frontend Security

XSS — Cross-Site Scripting

Injecting malicious scripts into pages that other users view. React escapes all JSX string values by default — <div>{userInput}</div> is safe. Only dangerouslySetInnerHTML can introduce XSS, and it must be avoided or sanitised with DOMPurify.

CSRF — Cross-Site Request Forgery

A malicious site tricks the user's browser into making authenticated requests. Mitigations:

  • SameSite=Strict cookies — browser won't send the cookie cross-origin
  • CSRF token — server issues a token that must be in every state-changing request header
  • Custom request header check — any request with a non-simple header (e.g. Content-Type: application/json) triggers a preflight, blocking CSRF from simple form posts

Content Security Policy (CSP)

14. Webhooks

What is a webhook?

A webhook is an HTTP POST from server to server triggered by an event. It's the inverse of an API call — instead of polling "did anything change?", the sender pushes a notification when something happens.

Inbound Webhooks (OpsOwl)

External systems (core banking, fraud detection) POST alerts to POST /api/v1/inbound/{source}. OpsOwl validates the payload, creates or enriches an alert, and optionally auto-assigns it to a case.

  Buffer.from(expected), Buffer.from(received)
);
How do you handle webhook delivery failures?
Exponential backoff with jitter: retry after 1s, 5s, 30s, 5min, 30min. After N attempts mark as "exhausted" and stop. Store every delivery attempt with its HTTP status code, error message, and timestamp — visible in the OpsOwl webhook deliveries log so admins can diagnose and manually replay. Idempotency: each webhook delivery has a unique ID in the payload so receivers can deduplicate retries. Timeout: set a short connect/read timeout (5–10s) — slow receivers shouldn't block the retry queue.

34. Rapid-fire Q&A

What is a closure and how does it cause stale state in hooks?
A closure captures variables from its surrounding scope at the time it's defined. In useEffect, the callback closes over state/props values at the time the effect was created. If the effect runs later without re-creating (because deps didn't change), it reads the old stale value. Fix: add the variable to the deps array, or store it in a useRef that's updated each render (the onEventRef.current = onEvent pattern from useTimelineSSE).
What is hydration and what causes hydration errors?
Hydration is React attaching event listeners to the HTML string rendered by the server, making it interactive. A hydration mismatch happens when the server-rendered HTML differs from what the client would render on first pass — e.g. using window or Date.now() in a Server Component, or conditional rendering based on localStorage. Fix: guard browser-only code with useEffect (runs only on client) or typeof window !== "undefined".
Explain the difference between useLayoutEffect and useEffect.
useEffect runs after the browser has painted. useLayoutEffect runs synchronously after DOM mutations but before paint. Use useLayoutEffect when you need to read DOM measurements (e.g. element width) and synchronously update state before the user sees a flash. In practice, 95% of cases use useEffect — useLayoutEffect is for scroll-restoration, tooltip positioning, etc.
How does Next.js Image component prevent CLS?
CLS occurs when images pop in without reserved space. next/image requires width and height props (or fill), which Next.js uses to set the CSS aspect ratio on the container before the image loads. The browser reserves the exact space, so no layout shift occurs when the image loads.
What is React 18's concurrent mode and when does it matter?
Concurrent mode allows React to interrupt, pause, and resume rendering work. Key APIs: useTransition (mark an update as non-urgent — keeps UI responsive), useDeferredValue (defer re-rendering a slow subtree), Suspense for async data. Practically: wrap expensive filter/sort updates in startTransition so the input stays responsive. In OpsOwl the cases list search uses a 300ms debounce to avoid concurrent-mode complexity, but a large app would benefit from useTransition on filter changes.
How would you implement micro-frontends?
Module Federation (Webpack 5) lets separate apps expose and consume components at runtime. Use when: multiple teams own different parts of the app, teams deploy independently, tech stacks diverge. Downsides: complex shared dependency management, no single bundle optimisation, higher coordination overhead. For most product companies (including OpsOwl), a well-structured monorepo with clear ownership boundaries is simpler and faster than micro-frontends.
How do you handle errors globally in a React app?
Three layers: (1) Error Boundaries (class components) catch render errors and show fallback UI — use Next.js error.tsx per route segment. (2) TanStack Query error state — all fetch errors surface via isError / error and can be caught globally in QueryClient onError. (3) Unhandled promise rejection — add window.addEventListener("unhandledrejection") and report to Sentry/DataDog. In OpsOwl, API 401s are caught in api.ts and trigger a silent refresh — this prevents most "session expired" error states from ever reaching the UI.
What's the difference between controlled and uncontrolled components?
Controlled: form state lives in React (value={state} + onChange). React is the source of truth — every keystroke re-renders. Good for validation, dependent fields, programmatic resets. Uncontrolled: DOM is the source of truth — read via ref.current.value on submit. Simpler for large forms where you only need the final value. Libraries like React Hook Form use uncontrolled inputs internally for performance.
How do you approach accessibility (a11y) in a complex app?
Semantic HTML first (<button> not <div onClick>, <nav>, <main>). ARIA labels for icons-only buttons. Keyboard navigation — every interactive element reachable via Tab, modals trap focus. Color contrast ≥ 4.5:1. role="alert" for dynamic status messages so screen readers announce them. Test with axe DevTools or @axe-core/playwright in CI. In OpsOwl's sidebar, every nav link is an <a> and active state is conveyed by both color and the aria-current="page" attribute.
As a Frontend Lead, how do you decide when to introduce a new dependency?
Check: (1) Bundle cost — run on bundlephobia.com; is it worth it? (2) Maintenance — last commit, GitHub stars, open issues trend. (3) Can we write it ourselves in <2 hours? — for simple utilities like timeAgo() (which OpsOwl implements inline at 10 lines), native > npm. (4) Security — npm audit, check CVEs. (5) Lock-in — is the API stable? Is there an escape hatch? Prefer small, single-purpose packages over large frameworks that own your architecture.

21. Browser Rendering Pipeline

Critical Rendering Path (CRP)

// Step 1: Parse HTML → DOM tree (incrementally, can be blocked by scripts)
// Step 2: Parse CSS → CSSOM tree (blocks rendering until complete)
// Step 3: DOM + CSSOM → Render Tree (visible nodes only — display:none excluded)
// Step 4: Layout (Reflow) — calculate exact position/size of every node
// Step 5: Paint — fill pixels: text, colors, images, shadows
// Step 6: Composite — combine painted layers in correct order (z-index, opacity)

// Goal: get to first paint as fast as possible
// Block: render-blocking CSS (in <head>), parser-blocking scripts (no async/defer)

Reflow vs Repaint vs Composite

OperationTriggered byCostFix
Reflow (Layout)Changing width, height, margin, padding, font-size; reading offsetWidth, getBoundingClientRectMost expensive — cascades to childrenBatch DOM reads/writes; use CSS transforms instead of top/left
RepaintChanging color, background, visibility, box-shadowMedium — re-paints affected layerAvoid in animation hot paths
Composite onlyCSS transform, opacityCheapest — GPU handles it; no reflow or repaintUse these for all animations
// BAD: reading layout then writing causes forced synchronous reflow
const w = el.offsetWidth;  // read (forces flush)
el.style.width = w + 10 + "px"; // write
const h = el.offsetHeight; // read again → SECOND forced reflow

// GOOD: batch reads, then writes
const w = el.offsetWidth;  // read
const h = el.offsetHeight; // read (same reflow)
el.style.width  = w + 10 + "px"; // write
el.style.height = h + 10 + "px"; // write (batched)

// BEST: use CSS transform — no reflow, GPU composited
el.style.transform = `translateX(${offset}px)`;

What happens when you call getBoundingClientRect() inside a React render?
It forces a synchronous layout flush (reflow). React batches DOM updates and applies them together; reading a layout property mid-batch forces the browser to flush those updates first to give you accurate measurements. This kills performance in loops. Always read layout properties in useLayoutEffect (after DOM mutations, before paint) or cache the result. Never read layout inside JSX render functions.

26. Form Management — React Hook Form + Zod

Why React Hook Form?

Uses uncontrolled inputs internally — no re-render on every keystroke. Only re-renders on submit, error change, and explicit watch(). For a 20-field form this is the difference between 20 re-renders per keystroke and zero.

import { useForm } from "react-hook-form";
import { z } from "zod";
import { zodResolver } from "@hookform/resolvers/zod";

// 1. Define schema with Zod
const caseSchema = z.object({
  title:       z.string().min(3, "Title must be at least 3 characters"),
  priority:    z.enum(["critical", "high", "medium", "low"]),
  description: z.string().optional(),
  due_date:    z.string().datetime().optional(),
});
type CaseForm = z.infer<typeof caseSchema>;  // auto-derive TypeScript type

// 2. Use in component
const { register, handleSubmit, formState: { errors, isSubmitting } } = useForm<CaseForm>({
  resolver: zodResolver(caseSchema),
  defaultValues: { priority: "medium" },
});

const onSubmit = async (data: CaseForm) => {
  await api.post("/api/v1/cases", data);
};

return (
  <form onSubmit={handleSubmit(onSubmit)}>
    <input {...register("title")} placeholder="Case title" />
    {errors.title && <span className="text-red-400">{errors.title.message}</span>}
    <button disabled={isSubmitting}>
      {isSubmitting ? "Creating..." : "Create Case"}
    </button>
  </form>

33. Behavioral Interview — STAR Answers from OpsOwl

Use OpsOwl as your project for every behavioral answer. Real product, real decisions, real tradeoffs.

Tell me about a time you made a significant architectural decision.
Situation: Building OpsOwl, a compliance investigation workspace. Needed to manage auth state (user, role) + server state (cases, tasks, documents) + real-time timeline events.

Task: Choose a state management approach that scales to 12+ features without becoming a maintenance burden.

Action: Introduced a two-layer model: Zustand for client/auth state (synchronous, persisted to sessionStorage), TanStack Query for all server state (async, cached, background-refreshed). Wrote an ADR documenting the tradeoffs. Defined a rule: if it comes from the API, it lives in TanStack Query. If it's UI state or auth, it lives in Zustand.

Result: Zero prop-drilling, no redundant API calls across 12 features, optimistic updates in <10 lines on any mutation. New engineers understand the model in under an hour.
Tell me about a time you improved performance significantly.
Situation: Cases list was re-rendering on every keystroke in the search input, causing noticeable lag at 200+ rows.

Task: Fix search performance without breaking existing filters.

Action: Three changes: (1) Moved client-side filter logic into a useMemo with stable deps. (2) Added 300ms debounce on server-side search query. (3) Switched server-side search to use a dedicated search endpoint (/api/v1/search?q=) instead of the cases list endpoint — so partial matches across all cases are returned, not just loaded pages.

Result: Search feels instant, no mid-type lag, and now searches across all cases (not just the loaded page). Verified in Playwright E2E tests.
Tell me about a complex real-time feature you built.
Situation: Case timelines needed to update live as multiple investigators worked on the same case simultaneously.

Task: Implement real-time updates without WebSockets (client requirement: must work behind corporate HTTP proxies).

Action: Built useTimelineSSE — a custom hook using Server-Sent Events. Key decisions: (1) SSE ticket endpoint (90s-lived token) so the full access token never appears in URLs. (2) ?last_event_id= on reconnect to replay missed events. (3) Manual reconnect with exponential backoff (1s→2s→4s→30s cap) instead of browser auto-reconnect which would use a stale token. (4) onEvent stored in a ref to avoid stale closure — handler always calls the latest callback without being in the dependency array.

Result: Timeline updates appear in <200ms. Reconnects invisibly in under 2 seconds. Tested with 318 Playwright E2E tests including reconnect scenarios.
How do you handle disagreements with backend engineers on API design?
Situation: Backend returned a flat list of case events; the frontend needed them grouped by date for the timeline view.

Approach: I first evaluate: is this transformation trivial on the frontend, or does it require data the backend already has? Grouping by date is a 5-line JavaScript reduce — no reason to put it in the API contract. However, if the grouping requires joining two tables or computing aggregates, the backend is the right place. I document the API contract in OpenAPI spec, propose both approaches with complexity estimates, and defer to whichever is cheaper to maintain. I never fight over "ownership" — I fight for the one that makes the product faster to ship and easier to maintain.
How do you manage technical debt in a fast-moving product?
In OpsOwl, we shipped 12 features in under 3 months. To keep debt from compounding: (1) Boy Scout Rule — leave the code cleaner than you found it; if you touch a file, fix obvious issues. (2) Debt tickets — when we take a shortcut intentionally, we create a ticket immediately with the tradeoff explained. (3) 20% capacity — every sprint allocates 20% to cleanup and refactor. (4) Automated guardrails — ESLint, TypeScript strict mode, and bundle size checks in CI catch a class of debt automatically. (5) Never refactor and add features in the same PR — makes review impossible and blame harder.

Audit Logging

Non-negotiable compliance infrastructure for regulated fintech and NBFC operations. Every user action, AI decision, data change, login event, and file access is recorded immutably — tamper-evident, partitioned, and retained for 7 years to satisfy RBI and SEBI audit requirements.

Go 1.26 PostgreSQL 18.4 River (batch jobs) PARTITION BY RANGE Row-Level Security OpenTelemetry Next.js 16 CSV Export
01

Feature Overview

Enterprise customers in fintech, NBFCs, and lending operations are regulated entities. They must be able to prove to external auditors — and regulators — exactly who did what, when they did it, and why. Audit logging is not a nice-to-have; it is the compliance foundation every other feature depends on.

The Regulatory Reality

  • RBI mandates tamper-proof audit trails for all digital lending platforms
  • SEBI requires complete action logs for licensed intermediaries
  • 7-year retention is the minimum regulatory requirement in India
  • Regulators can demand logs during inspections with no advance notice
  • Log tampering is a criminal offence — immutability is non-negotiable

What Audit Logging Enables

  • Forensic investigation after an incident or fraud event
  • Insider threat detection — who accessed which sensitive case
  • AI accountability — every AI action is traceable to a human approver
  • Change history reconstruction for any resource
  • Export evidence packs for regulators within minutes
🔒

Design constraint: The audit_logs table is append-only by design. No deleted_at column. No UPDATE. No soft-delete. PostgreSQL row-level security enforces INSERT + SELECT only for the application user. Violation attempts return a PostgreSQL permission error — not a business logic error.

< 0ms Impact on API response (async)
7 yr Mandatory retention period
100% Mutating operations covered

03

Immutability Design

🔒

audit_logs is append-only — by law, by design, by enforcement

No deleted_at column. No UPDATE path in the service layer. PostgreSQL RLS blocks UPDATE and DELETE at the database level. Tampering is impossible through the application stack.

No deleted_at Column

Every other table in OpsOwl AI uses soft-delete via deleted_at TIMESTAMPTZ. The audit_logs table intentionally omits this column entirely. Its absence is the design. A log entry cannot be "soft deleted" — it does not exist in the code model, the DDL, or the sqlc-generated queries.

No UPDATE in Service Layer

The internal/audit/service.go exposes only two operations: Insert and Query. There is no Update method, no Delete method. sqlc-generated queries for this table contain only INSERT and SELECT statements — no UPDATE or DELETE queries are generated.

PostgreSQL Row-Level Security

Even if a bug or malicious code somehow called UPDATE on audit_logs, PostgreSQL RLS stops it at the database level. The application database user is granted only INSERT and SELECT on this table. UPDATE and DELETE are explicitly denied.

-- Application role has INSERT + SELECT only
GRANT INSERT, SELECT ON audit_logs TO opsowl_app;

-- Superuser / migration role retains full access for partition management
GRANT ALL ON audit_logs TO opsowl_migrations;

-- RLS policy: app user can insert and select their tenant's rows
ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY;

CREATE POLICY audit_logs_insert_policy
  ON audit_logs
  FOR INSERT
  TO opsowl_app
  WITH CHECK (true);

CREATE POLICY audit_logs_select_policy
  ON audit_logs
  FOR SELECT
  TO opsowl_app
  USING (true);

-- No UPDATE policy, no DELETE policy → operations are rejected
✓

Defence-in-depth: Three independent immutability controls — no column, no service method, no DB permission. All three must be bypassed simultaneously to tamper with a log. This satisfies tamper-evident log requirements under RBI Digital Lending Guidelines.

Middleware Approach (Go)

Audit logging is fully automatic. Handlers never call the audit service manually. A single AuditMiddleware wraps all mutating routes and specific sensitive read routes, capturing metadata before and after each request, then dispatching an async River job for the actual write.

ℹ️

Key design choice: Audit entries are enqueued to River after the handler returns a successful response (2xx). Failed requests (4xx, 5xx) are not audited as completed actions. Authentication failures (auth.login_failure) are a special case — they are logged via the auth handler directly since the middleware can't determine the actor before auth completes.

// internal/audit/middleware.go

package audit

import (
  "context"
  "net/http"
  "time"

  "github.com/go-chi/chi/v5"
  "go.opentelemetry.io/otel/trace"
  "opsowl/internal/auth"
)

// mutatingMethods are intercepted unconditionally.
var mutatingMethods = map[string]bool{
  "POST": true, "PUT": true, "PATCH": true, "DELETE": true,
}

// sensitiveGetRoutes: specific GET routes also audited (data access).
var sensitiveGetRoutes = map[string]bool{
  "/api/v1/documents/{id}/download": true,
  "/api/v1/audit-logs/export":        true,
}

func AuditMiddleware(svc *Service) func(http.Handler) http.Handler {
  return func(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
      routePattern := chi.RouteContext(r.Context()).RoutePattern()
      isMutating   := mutatingMethods[r.Method]
      isSensitive  := sensitiveGetRoutes[routePattern]

      if !isMutating && !isSensitive {
        next.ServeHTTP(w, r)
        return
      }

      // Capture pre-request state (for update diffs)
      actor   := auth.ActorFromCtx(r.Context())
      traceID := trace.SpanFromContext(r.Context()).SpanContext().TraceID()
      meta := &RequestMeta{
        ActorID:   actor.ID,
        IP:        realIP(r),
        UserAgent: r.UserAgent(),
        RequestID: traceID.String(),
        OccurredAt: time.Now().UTC(),
      }

      // Pre-fetch current resource state for diff computation
      before, _ := svc.FetchResourceSnapshot(r.Context(), r)
      ctx := WithAuditBefore(r.Context(), before)

      // Wrap response writer to capture status code
      rw := NewStatusRecorder(w)
      next.ServeHTTP(rw, r.WithContext(ctx))

      // Only enqueue on success (2xx)
      if rw.Status >= 200 && rw.Status < 300 {
        after, _ := svc.FetchResourceSnapshot(r.Context(), r)
        svc.EnqueueAsync(r.Context(), meta, before, after)
      }
    })
  }
}

Route Registration (Chi)

The middleware is applied at the router group level, not globally, to avoid auditing health-checks, metrics, and public endpoints:

// cmd/api/router.go
r.Group(func(r chi.Router) {
  r.Use(middleware.Authenticate(jwtSvc))
  r.Use(audit.AuditMiddleware(auditSvc))  // ← applied here

  r.Mount("/api/v1/cases",     cases.Routes(caseHandler))
  r.Mount("/api/v1/documents", docs.Routes(docHandler))
  r.Mount("/api/v1/tasks",     tasks.Routes(taskHandler))
  // ...
})
06

Before / After State Capture

The payload JSONB column stores a rich diff of resource state. The shape of the payload depends on the operation type.

CREATE

Full object snapshot captured after successful insert.

{
  "created": {
    "id": "uuid...",
    "title": "...",
    "status": "open"
  }
}

UPDATE

Pre-fetch before, post-fetch after — only diff fields stored.

{
  "before": {
    "status": "open"
  },
  "after": {
    "status": "closed"
  }
}

DELETE

Full object snapshot at the moment of deletion.

{
  "deleted": {
    "id": "uuid...",
    "title": "...",
    "assignee": "..."
  }
}

Diff Computation Strategy

  • Pre-fetch: Middleware calls FetchResourceSnapshot() before the handler runs. The snapshot is stored in request context via WithAuditBefore(ctx, snapshot).
  • Post-fetch: After the handler returns 2xx, middleware fetches the updated resource again for the "after" snapshot.
  • Diff: Go struct comparison produces a map of only the changed fields — full objects are not stored for updates to keep payload size small.
  • Create/Delete: No diff — the full object is stored as-is. For deletes, the snapshot is captured before the handler runs (the "before" fetch), stored as {deleted: {...}}.
  • Sensitive fields: Fields in the AuditRedacted struct tag (e.g. password hashes, raw PAN) are stripped before storage.

Chain Integrity — Tamper Detection

Each audit log row stores a cryptographic chain hash linking it to the previous row. Any modification to an existing row breaks the chain, which is detectable during an integrity scan.

Hash Formula

// Computed in Go before enqueueing the River job
// chainHash = SHA256(prevRowID + occurred_at.RFC3339Nano + actorID + action)

func computeChainHash(prev ChainAnchor, e *AuditEntry) string {
  h := sha256.New()
  h.Write([]byte(prev.ID.String()))
  h.Write([]byte(e.OccurredAt.Format(time.RFC3339Nano)))
  h.Write([]byte(e.ActorID.String()))
  h.Write([]byte(string(e.Action)))
  return hex.EncodeToString(h.Sum(nil))
}

↓
#3

OpenTelemetry Integration

The request_id column in audit_logs is the OpenTelemetry trace ID for the HTTP request that triggered the action. This creates a three-way correlation between structured logs, distributed traces, and audit records.

Full Observability Chain

HTTP Request arrives
  │
  ├─ OTel middleware assigns Trace ID: 4bf92f3577b34da6...
  │
  ├─ Zap logger: {"trace_id": "4bf92f3577b34da6...", "msg": "PUT /api/v1/cases/uuid"}
  │
  ├─ Handler executes → case status updated
  │
  ├─ AuditMiddleware enqueues River AuditJob:
  │    { request_id: "4bf92f35-77b3-4da6-...",   ← trace ID stored here
  │      action: "case.status_changed", ... }
  │
  └─ Grafana Tempo: trace 4bf92f3577b34da6
       ├─ span: authenticate
       ├─ span: db.update_case_status (2ms)
       └─ span: river.enqueue_audit_job (<1ms)

What This Enables

  • Given an audit log entry → jump directly to the Grafana trace
  • Given a trace → find the audit log row for that exact request
  • Correlate slow queries (Tempo) with the action that caused them (audit log)
  • "Show everything that happened in this specific user session" — filter by actor + time range in both systems

Implementation Notes

  • Trace ID extracted via trace.SpanFromContext(ctx).SpanContext().TraceID()
  • Stored as UUID-formatted string in request_id column
  • Zap logger middleware also injects trace_id into every log line for the request
  • Grafana dashboard: "Audit + Trace correlation" view ships in Phase 1

River AuditInsertJob — Batch Design

// internal/audit/job_handler.go

type AuditInsertArgs struct {
  Entries []AuditEntry `json:"entries"`
}

type AuditInsertWorker struct {
  db      *pgxpool.Pool
  chainSvc *ChainService
  river.WorkerDefaults[AuditInsertArgs]
}

func (w *AuditInsertWorker) Work(ctx context.Context, job *river.Job[AuditInsertArgs]) error {
  entries := job.Args.Entries
  if len(entries) == 0 { return nil }

  // Fetch last chain anchor (most recent row in partition)
  anchor, _ := w.chainSvc.LatestAnchor(ctx)

  // Compute hashes and build batch insert values
  rows := make([]AuditRow, len(entries))
  for i, e := range entries {
    e.ChainHash = computeChainHash(anchor, &e)
    rows[i] = e.ToRow()
    anchor = e.AsAnchor()
  }

  // Single bulk INSERT
  return bulkInsert(ctx, w.db, rows)
}

// Batch scheduling: producer collects events for 100ms or 50 entries
const (
  batchWindow = 100 * time.Millisecond
  batchSize   = 50
)

Performance

< 1ms Write path overhead (async River enqueue)
1 partition Scanned per date-filtered query
streaming CSV export — no full-table memory load

Write Path

  • Middleware enqueues a River job in-process — no network round trip
  • River job executes asynchronously in a background worker
  • Batch window: 100ms or 50 events — whichever comes first
  • Bulk INSERT reduces per-row overhead by 40-60x vs individual inserts
  • Zero impact on API response time — users never wait for audit writes

Read Path

  • All queries include occurred_at range → PostgreSQL partition pruning kicks in
  • Monthly partition = each query scans at most 31 days of rows
  • Composite indexes on (actor_id, occurred_at DESC) and (case_id, occurred_at DESC) make common access patterns index-only scans
  • Cursor pagination avoids OFFSET scans — O(log n) per page

Phase 2 — Archival Strategy

Partitions older than 2 years will be detached from the live table and archived to S3 (cold tier). For compliance investigations requiring archived data:

  • Phase 2: Re-attach the partition temporarily for the investigation window
  • Phase 2: S3 Foreign Data Wrapper (aws_s3 or parquet_fdw) for read-only queries against archived partitions without re-attach
  • Archival cadence: quarterly batch job, run by River cron

Test Strategy

Middleware Intercept Tests

✓
Every POST creates an audit entry
Table-driven test over all POST routes verifies River job is enqueued with correct action and resource_type.
✓
Every PUT/PATCH creates an audit entry with diff
Verifies payload has before and after keys and that changed fields are present.
✓
Every DELETE creates an audit entry with deleted snapshot
Verifies payload has deleted key with full object captured before deletion.
✓
Failed requests (4xx/5xx) do NOT create audit entries
Verifies River job is not enqueued when handler returns a non-2xx status.
✓
Sensitive GET routes are intercepted
document download and audit export routes create document.downloaded entries.

Immutability Tests

✓
Service has no Update method
Static analysis / reflection test verifies AuditService exposes only Insert and Query.
✓
PostgreSQL rejects UPDATE on audit_logs
Integration test connects as opsowl_app role, attempts UPDATE, asserts pgx permission error.
✓
PostgreSQL rejects DELETE on audit_logs
Same as above for DELETE — asserts pgx permission error, not a silent no-op.
✓
sqlc generates no UPDATE/DELETE queries
CI step asserts audit.sql contains only SELECT and INSERT statements.

Chain Integrity Tests

✓
Sequential inserts produce valid chain
Insert 100 rows, run VerifyChainIntegrity — asserts all hashes are valid and linked.
✓
Tampered row breaks chain
Directly modifies a row in test DB (superuser), re-runs VerifyChainIntegrity — asserts broken chain is detected at the correct row.
✓
Genesis row hash is deterministic
First row always uses zero UUID as previous ID — test verifies hash is stable across restarts.

Export & Partition Tests

✓
CSV export format is correct
Parses exported CSV, verifies column headers, UTF-8 encoding, and that date values are ISO 8601 UTC.
✓
CSV export is streamed (not buffered)
Instruments memory allocator — asserts peak heap during 10k-row export is below 5MB.
✓
Export rejects missing date range
Asserts 400 response when date_from or date_to is absent.
✓
Partition routing correctness
Inserts rows dated to three different months, queries with EXPLAIN, asserts only the relevant partition is scanned (no cross-partition scan).

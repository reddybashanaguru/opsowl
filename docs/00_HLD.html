Product Overview

OpsOwl AI is an AI-native enterprise investigation and operations workspace purpose-built for fraud analysts, compliance officers, and risk operations teams inside fintech startups, NBFCs, lending platforms, and compliance consultancies. It replaces fragmented spreadsheets, email chains, and disconnected tools with a single structured workspace where cases are opened, investigated with AI assistance, documented with an immutable audit trail, and closed with full evidentiary integrity.

📊 Primary ICP
Fintech startups, NBFCs, lending ops teams, compliance consultancies, risk operations. 10–500 seat teams who run investigations on customers, transactions, and entities.
✨ Core Value Prop
AI-assisted case investigation with structured timelines, document intelligence, collaborative notes, immutable audit trail, and human-review gates — all within a multi-tenant, RBAC-governed workspace.
🛡 Compliance-First
Every AI action is logged, explainable, and human-reviewable. PII is masked before every LLM call. Schema-per-tenant isolation. Event-sourced audit trail is tamper-evident by design.

Key Differentiators

✓
Investigation-native UX: Timeline workspace with thread-based evidence and AI-generated summaries tailored to ops analysts, not generic project management.
✓
AI with guardrails: Provider-agnostic LLM router (Anthropic + OpenAI abstraction), PII masking pipeline, and AI Action Ledger — every AI output is traceable, reviewable, and correctable.
✓
Enterprise governance: Schema-per-tenant from day one, RBAC at middleware level, RS256 JWT auth, event sourcing for compliance, and full audit logging on every state change.
✓
Lightweight infrastructure: PostgreSQL-only for MVP (pgvector, River job queue) — no Redis, no Elasticsearch, no separate vector DB. Upgrade thresholds are defined, not speculative.

OpsOwl AI uses a 6-layer modular architecture. The layers are strictly ordered — upper layers never bypass lower layers. All cross-cutting concerns (auth, rate limiting, audit interception) live in the API Gateway layer.

Monolith boundary: Go modules (L3) compile into a single binary. They share the same Postgres connection pool but never issue cross-schema SQL joins. Inter-module calls go through Go interfaces, making future service extraction a rename not a rewrite.

Data Flow

Standard API Request Flow

🌐
Browser → Next.js API Route / Client fetch
TanStack Query issues fetch() with Authorization: Bearer <access_token>. Server Components fetch on the server. Client Components fetch in the browser. Optimistic updates applied immediately to local cache.
🔐
API Gateway — Auth & RBAC Middleware
Chi router receives request. JWT RS256 verified (golang-jwt). Claims extracted: sub, tenant_id, roles[]. RBAC guard checks route permission. Rate limit checked (sliding window, Postgres-backed). Request ID injected into context. Audit hook registered on response.
⚙️
Core Service Module
Handler calls service layer. Service validates business rules (e.g. case ownership, status machine). sqlc query executed against tenant schema (SET search_path = tenant_<id>). Transaction wraps mutations + audit event insert. River job enqueued if async work needed (doc processing, email send).
🗄️
PostgreSQL — Tenant Schema
Query runs inside tenant's schema. Immutable audit event appended. If doc upload, River job inserted with file reference. Response rows returned.
📤
Response Envelope → Browser
Response formatted: { data: T, meta: { request_id, timestamp }, error: null }. Audit hook fires: writes audit log row asynchronously. TanStack Query cache updated. UI reflects new state.

AI Request Flow

🤖
User triggers AI Copilot action
Browser sends POST to Go API Gateway (/v1/ai/copilot/ask) with case_id and user query. SSE connection opened for streaming response.
🔐
Go API Gateway validates & proxies
JWT verified, RBAC checked (copilot:read permission). Go backend calls Python AI service via internal HTTP. Passes: masked_context, case_id, tenant_id, user query.
🧠
Python AI Service — PII Masking → RAG → LLM
PII masker replaces names, PAN, Aadhaar, phone numbers with tokens before any LLM call. Embedding generated for query. pgvector cosine search retrieves top-k relevant case chunks. Prompt assembled: system prompt (from registry) + context chunks + user query. LLM Router selects provider (Anthropic Claude primary, GPT-4o fallback). Response streamed back.
📋
AI Action Ledger Written
Every AI call logged: prompt_hash, masked_input, raw_output, provider, model, tokens_in, tokens_out, latency_ms, pii_entities_masked, needs_human_review flag, case_id, user_id, timestamp.
📡
SSE Stream → Browser
Tokens streamed via SSE. Browser Copilot panel renders tokens progressively. On completion, human review flag surfaced if confidence below threshold. Full response stored in AI ledger.

Database Schema Strategy

Schema-Per-Tenant
Every tenant gets a dedicated PostgreSQL schema (tenant_<uuid>). The public schema holds only the tenants registry and global config. Queries set search_path at connection time. No row-level-security required; isolation is schema-level. Makes tenant data export and deletion trivial.
Event Sourcing (Audit)
Every state-changing operation appends an immutable event to audit_events. Events are never updated or deleted. Current state is derived by applying events in order. This provides a tamper-evident compliance trail that regulators can export and verify.

Key Tables (per-tenant schema)

timeline_events UUID case_id, event_type, occurred_at, actor_id, payload JSONB, sequence_num Append-only. sequence_num enforces ordering. Immutable after insert.

⚠️
App DB user permissions: The application Postgres user has INSERT but NOT UPDATE/DELETE on audit_events and ai_action_ledger. Deletion of these tables requires a separate privileged migration user — enforced at DB level, not just application level.

Security Architecture

Authentication Flow (JWT RS256)

1. POST /v1/auth/login  { email, password }
   └─ bcrypt.Compare(password, hash, cost=12)
   └─ Sign access_token  (RS256, 1hr, private key)
   └─ Sign refresh_token (RS256, 7d, private key)
   └─ Store refresh_token hash in DB (refresh_tokens table)
   └─ Return { access_token, refresh_token, expires_in }

2. Every authenticated request:
   Authorization: Bearer <access_token>
   └─ golang-jwt validates RS256 signature (public key)
   └─ Checks exp, iat, iss, aud claims
   └─ Extracts: sub (user_id), tenant_id, roles[]
   └─ Injects into Go request context

3. POST /v1/auth/refresh  { refresh_token }
   └─ Hash incoming token → compare with DB
   └─ Issue new access_token + rotate refresh_token
   └─ Old refresh_token invalidated (single-use)

4. POST /v1/auth/logout
   └─ Delete refresh_token row from DB
   └─ Access token naturally expires (1hr)

PII Masking Pipeline

🔍
PII Detection
Named entity recognition on input text. Detects: full names, email addresses, phone numbers, PAN numbers, Aadhaar numbers, bank account numbers, IFSC codes, IP addresses, dates of birth.
🎭
Token Substitution
Each PII entity replaced with deterministic token: [PERSON_1], [PHONE_2], [PAN_1]. Token map stored in memory for the duration of the AI call only — never persisted.
🚀
Masked Payload → LLM
Only masked text sent to LLM provider. Raw PII never leaves the server. AI Action Ledger stores masked version only.
🔄
Response De-tokenisation
LLM response may contain tokens. De-tokeniser replaces [PERSON_1] → original value in response shown to user. De-tokenisation happens in-process; tokens never stored post-call.
09

AI Architecture

LLM Router
Provider-agnostic interface. Primary: Anthropic Claude (claude-3-5-sonnet). Fallback: OpenAI GPT-4o. Routing logic: task type, cost threshold, latency SLA, provider health. Same Python interface regardless of provider — swap without code changes.
Prompt Registry
All system prompts stored in prompt_registry table (versioned). Prompts parameterised with Jinja2 templates. New prompt versions require human approval before going live. Rollback to previous version in one DB update.
RAG Pipeline
Query → embed (text-embedding-3-small or Cohere) → pgvector IVFFlat cosine search → top-k chunks retrieved → re-rank by relevance → inject into prompt context. Chunking: 512 tokens with 64-token overlap.
Human Review Gates
AI actions flagged for human review when: confidence score < 0.7, sensitive action (case closure recommendation), new document type seen, PII masking detected ambiguous entities. Flagged items appear in analyst review queue before action taken.
AI Action Ledger
Every AI inference logged: provider, model, version, masked_prompt_hash, tokens, latency, pii_count, output_summary, case_id, analyst_id. Enables cost tracking, quality review, compliance audit, and model migration analysis.
Guardrails
Output validation: hallucination detection on cited document references, citation verification against case documents, refusal on out-of-scope queries, max token budget per call, rate limit per user per day.

API Standards

Versioning
All endpoints prefixed with /v1/. Breaking changes require new version prefix. Non-breaking additions (new optional fields) allowed without version bump. Version sunset minimum 6 months notice.
Date & ID Format
All dates: ISO 8601 UTC strings — 2026-05-16T10:30:00Z. All IDs: UUID v4 in string form. Never expose sequential integer IDs in API responses.

Response Envelope

// Success
{
  "data": { ... },          // typed payload
  "meta": {
    "request_id": "uuid",
    "timestamp": "ISO8601",
    "page": 1,              // present when paginated
    "per_page": 20,
    "total": 143,
    "has_next": true
  },
  "error": null
}

// Error
{
  "data": null,
  "meta": { "request_id": "uuid", "timestamp": "ISO8601" },
  "error": {
    "code": "CASE_NOT_FOUND",     // machine-readable constant
    "message": "Case not found",  // human-readable
    "details": { "case_id": "..." }
  }
}

GET /v1/cases?page=2&per_page=20&sort=created_at&order=desc

// Cursor-based (timeline events — infinite scroll)

AI Responses — Async / Streaming
AI Copilot responses are not bound by synchronous latency SLAs. First token streamed within 2s target. Full response typically 5–30s depending on context size. All AI calls are async — UI shows progressive streaming, never a blocking spinner.
Document Processing — Background
Document upload returns immediately (201 ACCEPTED). Processing (OCR → embed → index) happens via River job. Target: <60s for a 20-page PDF. Status polled by frontend via GET /v1/documents/:id every 3s until DONE.

Phase 2 Roadmap

The following technologies and features are deliberately deferred from MVP. Each has a specific trigger condition based on measured load or usage data — not speculative. Adding them before the trigger wastes engineering capacity and operational complexity.

Technology / Feature What It Adds Trigger Condition Current MVP Alternative
Redis Read cache for hot data (case lists, dashboards), session store, distributed rate limiting DB read p99 > 200ms sustained, or 50+ concurrent active users PostgreSQL-backed cache; River on Postgres for queues
Elasticsearch Advanced full-text search, faceted filters, typo tolerance, cross-tenant search Full-text search p99 > 500ms, or search becomes a user-reported pain point PostgreSQL tsvector + GIN index + pgvector semantic
ClickHouse Fast OLAP analytics, high-cardinality aggregations, time-series dashboards at scale Dashboard aggregation query > 1s at p50, or analytics becomes a product differentiator PostgreSQL aggregation queries; materialized views
GraphQL Flexible client-driven queries, reduced over-fetching, subscription support Multiple distinct client types (mobile, embedded) with divergent data needs REST API with response envelope; typed endpoints per feature
Entity / Knowledge Graph (MOD-02) Cross-entity relationship traversal, fraud ring detection, network analysis Customer request + 3+ enterprise deals requiring graph analysis Case-level entity lists in JSONB; manual linking
Workflow Engine (MOD-06) Configurable SLA workflows, automated escalation, approval gates Customer request for configurable workflows in 2+ enterprise deals Manual case status progression with task checklists
Integration Framework (MOD-13) Webhook outbound, Slack/Teams, JIRA, core banking connectors Integration request from 2+ paying customers Manual export, email notifications via Resend
Kubernetes Horizontal scaling, auto-healing, rolling deployments, multi-region Single-host Docker Compose hits CPU/memory ceiling, or 3+ tenants active Single-host Docker Compose with manual restarts
ℹ️
Architecture is Phase-2 ready: The modular monolith structure, schema-per-tenant DB design, provider-agnostic AI abstraction, and Docker service topology are all designed to accommodate Phase 2 additions without re-architecting. Phase 2 is an addition, not a rewrite.

SLA Policies
/sla
Why it exists

RBI, FIU-IND, and SEBI mandate investigation turnaround times. Without enforced SLA, cases age silently in queues and "case aged beyond regulatory TAT" becomes the most common examination finding. There is no automated signal when a deadline is approaching — the breach is discovered after it happens.

How it helps

4 fixed policies (Critical / High / Medium / Low) each with 3 controls: Warning Hours — private analyst notification before anything turns amber. Warning % of Breach — when the case row turns amber platform-wide. Breach Hours — hard regulatory deadline, case turns red and manager is alerted. The three layers give advance warning before a breach, not just a notification after it.

🔵 Example 1 — Critical Sanctions Hit (3-layer timeline)

A sanctions hit arrives at 2:00 PM. Critical SLA = 4h breach. At 4:00 PM (2h elapsed = Warning Hours), analyst Divya gets a private notification: "Your sanctions case needs attention — 2 hours remaining." At 5:00 PM (3h = 80% of 4h), the case row turns amber on the dashboard — everyone sees it. At 6:00 PM (4h = breach), the case turns red, the manager receives an alert.

🟣 Example 2 — Tightening SLA After a Regulatory Letter

RBI sends a letter requiring all high-priority AML investigations to be resolved within 12 hours (down from 24). CCO opens SLA Policies, edits the High policy: Breach Hours = 12, Warning % = 80 (amber at 9.6h), Warning Hours = 8 (analyst notified at 8h). From this moment, every new High case gets the updated SLA clock. Historical cases are not affected — only new ones.

Investigation Playbooks
/settings/playbooks
Why it exists

Under pressure — high volumes, tight deadlines — investigators skip steps. A KYC check is missed. A counterparty is not screened. The STR decision is made without documenting rationale. In regulatory examinations, missed steps become findings. Excel and email cannot enforce investigation procedure — it relies entirely on individual discipline.

How it helps

A playbook is triggered by case_type — when a case of matching type is created, all playbook steps are auto-created as tasks on that case instantly. Each step has a title, priority, due date (hours from case creation), and a dependency ("After step N") — the step is BLOCKED until its dependency is completed. This enforces investigation sequence, not just a checklist. The Case Type registry (shared with case creation) prevents typo mismatches that silently break the trigger.

Assignment Rules
/settings/assignment-rules
Why it exists

When alerts arrive during high-volume periods, cases sit unassigned. A manager manually reads each alert, decides which analyst to route it to, and makes the assignment. This creates a triage bottleneck. If the manager is unavailable, cases queue up. Senior analysts get overloaded while junior ones have capacity. There is no audit evidence of why a case was routed to whom.

How it helps

Rules fire synchronously at case creation (same HTTP request, under 1 second). Rules are evaluated in priority_order ASC — first match wins. Match conditions: Priority + Case Type (both optional, AND logic). Assignment modes: Specific User (direct routing) or Role round-robin (picks the analyst/manager with fewest open cases at that moment — automatic load balancing). If no rule matches, the system falls back to the least-loaded manager → admin → super_admin. Nothing ever stays unassigned.

Why it exists

Every bank has a TMS (Transaction Monitoring System) that fires alerts. Today those alerts arrive in email, Excel exports, or a separate queue — and a human manually reads each one to decide if it needs a case. This is slow, error-prone, and creates a gap between when the alert fires and when the investigation starts. That gap is where regulatory breaches happen.

How it helps

The webhook URL is always visible on the source card with a copy button. Alert Routing Rules: evaluated in sort_order ASC, first match wins. Match on: alert type + min risk score. Set: priority mapping, mode (queue = analyst reviews manually, auto = case created immediately), dedup window (same entity+type within N hours = skipped), case type (which playbook to trigger).

Why it exists

In examination, the question is not just "what happened?" but "can you prove what happened and that no one tampered with the record?" Without tamper-evidence, any log can be altered after the fact. SHA-256 hash-chaining is the technical standard for tamper-evident audit trails — each entry contains the hash of the previous one, making any alteration mathematically detectable.

SHA-256 hash chain links every entry to the previous one — any tampering breaks the chain and is immediately detectable. Filter by user, action type, and date range. Export audit log for examination submission — provide the complete record without granting system access. Even failed login attempts are recorded.
